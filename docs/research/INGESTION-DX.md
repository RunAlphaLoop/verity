# Research Digest — Ingestion DX & Bring-Your-Own-Token (July 2026)

> 4-track research sweep behind SPEC.md §5e. Companion: MERGE-EVALUATION.md, ALLOY-EVALUATION.md.

## pat-coverage

BYOT (bring-your-own-token) coverage survey, verified against primary sources July 2026: ALL 20 surveyed systems let a customer self-provision a first-party credential (API key, PAT, private app, service account, or self-registered app in their own tenant) WITHOUT the vendor (us) registering a hosted OAuth app. Hosted OAuth clients are only required for multi-tenant SaaS distribution — exactly the cloud-edition problem Merge/Nango already covers. Webhooks work under first-party auth in ~18/20 systems (caveats: HubSpot private-app webhooks are UI-configured only; Google/Microsoft push requires a public verified HTTPS endpoint; Slack Socket Mode removes even that requirement). ACL/permission metadata readability is the real differentiator, not auth: file/content platforms (Drive, SharePoint/Graph, Box, Dropbox, GitHub, Jira/Confluence, Salesforce) expose full per-object ACLs under key auth; collaboration/SaaS tools (Notion, Gong, Intercom, Front, Monday, Airtable) expose partial or no per-object ACLs — these need Verity's quarantine/admin-visibility-policy path regardless of auth mechanism. Two live migrations matter for 2026 roadmaps: Zendesk is killing API tokens entirely (Jun 2026–Apr 2027, replaced by customer-created OAuth clients with client_credentials — still self-serve, but the connector must mint tokens), and Atlassian is expiring classic unscoped API tokens (pre-Dec-2024 tokens expired by May 2026; scoped tokens must call api.atlassian.com gateway URLs). Net answer to the design question: essentially 100% of the connector AUTH problem disappears for the OSS core if you target BYOT; what remains is (a) token-lifecycle plumbing for 3-4 systems that now use short-lived/client-credentials tokens, (b) webhook endpoint reachability, and (c) the ACL-fidelity gap, which is a product moat, not an auth problem.

### Findings
- **HubSpot: Private apps (created in customer's own portal, scoped access token) — full API coverage, no OAuth registration needed. Webhooks ARE supported in private apps but subscriptions must be configured in the private app's in-app settings UI, not via API. New 'Service Keys' (public beta Feb 10, 2026) explicitly do NOT support webhooks. ACL: CRM ownership/team fields readable, but HubSpot has no per-record ACL API — visibility is role/team-based and not fully exposed. [Documented: developers.hubspot.com/docs/guides/crm/private-apps/webhooks; developers.hubspot.com/changelog/service-keys. ACL gap: inferred from API surface]** — _https://developers.hubspot.com/docs/guides/crm/private-apps/webhooks_
  - Implication: BYOT works day one. Connector setup docs must include a 'click these webhook subscriptions in the UI' step (cannot automate). Use legacy private apps, not Service Keys, for push freshness. CRM records need an admin-assigned visibility policy (e.g., team-scoped) rather than true ACL mirroring.
- **Salesforce: Customer creates their own Connected App / External Client App in their own org and uses OAuth 2.0 client_credentials — self-serve, no vendor registration. The Sept 2025 security changes block UNINSTALLED (vendor-distributed) connected apps by default and killed device flow; customer-created, org-installed apps are unaffected and are now the recommended pattern. CDC/webhooks: Change Data Capture via Pub/Sub API works under the same connected-app token. ACL: sharing model is fully queryable (ObjectPermissions, *Share tables e.g. AccountShare, PermissionSetAssignment via SOQL). [Documented: help.salesforce.com Use Any API Client advisory; admin.salesforce.com Sept 2025 blog. ACL queryability documented; practical reconstruction complexity inferred]** — _https://admin.salesforce.com/blog/2025/get-ready-for-changes-to-connected-app-usage-restrictions_
  - Implication: The 2025 crackdown actually strengthens the BYO-app story — vendor-hosted OAuth apps got HARDER to distribute to Salesforce orgs, while customer-created apps stayed easy. Verity's native Salesforce connector should instruct customers to create their own connected app (5 min, admin-only). ACL mirroring is possible but Salesforce sharing recalculation is the hardest of the 20 — budget accordingly.
- **Google Workspace/Drive: Service account + domain-wide delegation, configured by the customer's super admin in their own Admin console — no Google app verification needed for internal-only use. Webhooks: changes.watch push notifications work with a service account but require a public HTTPS endpoint the customer controls. ACL: permissions.list returns the complete per-file ACL (users, groups, domains, anyone-links) — best-in-class. [Documented: knowledge.workspace.google.com DWD docs; developers.google.com/workspace/drive/api/guides/push]** — _https://developers.google.com/workspace/drive/api/guides/push_
  - Implication: Gold-standard BYOT target and already a flagship connector: full ACL fidelity + push + no OAuth client. Keep native. Only friction is super-admin involvement for DWD and a reachable webhook endpoint (offer changes.list polling fallback).
- **Microsoft 365/SharePoint: Customer registers an app in THEIR OWN Entra tenant (client credentials, app-only) — 'app registration' here is self-serve tenant config, not vendor OAuth distribution. Sites.Selected application permission scopes access to specific sites/lists/files (now supports both delegated and application modes). Graph change notifications + delta queries work app-only for drives/lists. ACL: /permissions endpoints on driveItems/sites return full ACLs. [Documented: learn.microsoft.com/graph/permissions-selected-overview; Graph webhooks docs]** — _https://learn.microsoft.com/en-us/graph/permissions-selected-overview_
  - Implication: BYOT works with zero vendor involvement; Sites.Selected answers the enterprise 'don't give it the whole tenant' objection. Needs public HTTPS notification endpoint. Full ACL fidelity achievable — keep native flagship status.
- **Slack: Customer creates their own app at api.slack.com/apps in their workspace — bot token (xoxb) + Events API. Socket Mode (app-level token, WebSocket) delivers events with NO public endpoint, but Socket Mode apps cannot be Marketplace-listed (irrelevant for BYOT). ACL: conversations.members gives channel membership; bot only sees channels it's invited to; Enterprise Grid Discovery API (org-wide + DMs) requires Org Owner and Slack approval. [Documented: docs.slack.dev/apis/events-api/using-socket-mode. Discovery API gating: documented but approval process partly inferred]** — _https://docs.slack.dev/apis/events-api/using-socket-mode/_
  - Implication: Excellent BYOT fit — Socket Mode is a killer feature for the OSS core: real-time push with zero networking setup (works behind firewalls). Channel-membership-as-ACL maps cleanly to Verity's model. Don't promise org-wide DM ingestion; that's Discovery-API territory.
- **Notion: Internal integration token, created self-serve per workspace. As of 2025, integration webhooks exist (configured in integration settings; events for pages, databases, data sources, comments) — a major upgrade from poll-only. ACL: the API does NOT expose per-page permission lists; an integration only sees pages explicitly shared with it, and enterprise 'what can this connection access' controls are admin-side, not readable. [Documented: notion.com/help/create-integrations-with-the-notion-api; webhook guides 2025; ACL non-exposure documented in help center + API reference]** — _https://www.notion.com/help/create-integrations-with-the-notion-api_
  - Implication: BYOT + push both work now. But ACL-rides-with-content CANNOT be satisfied from the API — Notion content must flow through quarantine or an explicit admin visibility policy (e.g., 'everything shared with this integration is visible to group X'). Document this loudly.
- **Confluence/Jira (Atlassian Cloud): User API tokens AND dedicated service-account API tokens, now with scopes. LIVE MIGRATION: classic tokens created before Dec 15, 2024 expired between Mar 14 and May 12, 2026; scoped tokens must use api.atlassian.com gateway URLs (not mysite.atlassian.net). Webhooks: admin-registered via system settings or REST. ACL: Jira issue security levels/project permissions and Confluence space permissions + page restrictions are readable via REST. [Documented: support.atlassian.com manage-api-tokens docs; developer.atlassian.com basic-auth deprecation notice]** — _https://support.atlassian.com/atlassian-account/docs/manage-api-tokens-for-your-atlassian-account/_
  - Implication: BYOT works but connectors written against pre-2025 token patterns are breaking RIGHT NOW — build against scoped tokens + api.atlassian.com from day one. Service-account tokens (not personal ones) are the right recommendation for durability. ACL fidelity achievable.
- **Zendesk: HARD DEPRECATION — API tokens are being removed entirely: unused tokens deactivated from Jul 28, 2026; no new tokens after Oct 27, 2026; all dead Apr 30, 2027, no opt-out. Replacement: customer creates an OAuth client in their own Admin Center and uses client_credentials or authorization_code grants — still fully self-serve, no vendor registration. Webhooks: created in Admin Center or via API; webhook auth via bearer/OAuth. ACL: ticket visibility is group/org/brand-based, readable via API. [Documented: support.zendesk.com article 10840968198042]** — _https://support.zendesk.com/hc/en-us/articles/10840968198042-Announcing-the-removal-of-API-tokens-as-an-authentication-method-for-API-requests_
  - Implication: Do NOT build a Zendesk connector on API tokens in 2026. The BYOT story survives (customer-created OAuth client + client_credentials = effectively a key), but the SDK needs a client_credentials token-minting helper. This is the leading indicator: 'API key' is trending toward 'self-registered OAuth client with machine grants' — design the SDK's credential abstraction around that.
- **Linear: Personal API keys (Settings > Security & Access), restrictable to read/write/admin scopes; admins and permitted members can create. Webhooks: first-class, created via settings or API, push on create/update. ACL: team membership (including private teams) queryable via GraphQL for what the key's user can see. [Documented: linear.app/docs/api-and-webhooks. Private-team ACL mapping: inferred from API surface]** — _https://linear.app/docs/api-and-webhooks_
  - Implication: Near-zero-friction BYOT + push. Key inherits the creating user's visibility — recommend a dedicated service user so ingested scope is explicit and stable.
- **Asana: Personal Access Token, self-serve. Webhooks are established via API using the PAT (X-Hook-Secret handshake; webhook lifetime is tied to the creating token — token revoked = webhook gone). ACL: project/team membership readable; PAT sees only what its user sees. [Documented: developers.asana.com/docs/personal-access-token and /docs/webhooks-guide]** — _https://developers.asana.com/docs/webhooks-guide_
  - Implication: Full BYOT + programmatic push. The webhook-dies-with-token coupling means the connector must monitor token health and re-establish webhooks — build that into the SDK's health-check lane.
- **GitHub: Fine-grained PATs (50+ granular permissions, per-repo/org scoping) OR a customer-created GitHub App in their own org (no marketplace listing needed). Repo/org webhooks fully manageable via REST with the Webhooks permission. ACL: collaborators, teams, and permission levels readable via REST. [Documented: docs.github.com fine-grained PAT permissions reference; REST webhooks docs]** — _https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens_
  - Implication: Complete BYOT story including programmatic webhook creation and full ACL reads. Customer-created GitHub Apps are the durable option (higher rate limits, non-user-bound) — offer both in docs.
- **Intercom: Private app in the customer's own Developer Hub yields a workspace access token — explicitly blessed for accessing your own workspace. Webhooks: configured on the app in Developer Hub UI (not via API); private apps receive events from their own workspace. ACL: Intercom conversation data is essentially workspace-global to teammates; no per-object ACL API. [Documented: developers.intercom.com/docs/webhooks and authentication docs. ACL flatness: inferred]** — _https://developers.intercom.com/docs/webhooks_
  - Implication: BYOT + push work; webhook config is a manual UI step. Flat permission model means a simple workspace-level visibility policy suffices — low quarantine risk.
- **Front: API tokens with scopes, self-serve. Two webhook paths under token auth: rule webhooks (per-rule HTTP POST, HMAC-SHA1 signed with API secret) and application webhooks (features on self-created apps on the Developers page). ACL: teammate and inbox-access endpoints exist to reconstruct who sees which inbox. [Documented: dev.frontapp.com/docs/webhooks-1, /docs/rule-webhooks. ACL reconstruction: inferred from endpoint surface]** — _https://dev.frontapp.com/docs/rule-webhooks_
  - Implication: Full BYOT + push. Inbox-membership is the natural ACL unit and appears reconstructable — mid-effort ACL fidelity.
- **Airtable: Personal Access Tokens with explicit scopes and per-base/workspace resource grants; webhook:manage scope enables the full Webhooks API (create/list/refresh) programmatically under a PAT. ACL: base/workspace collaborator reads exist mainly in the Enterprise API tier. [Documented: airtable.com/developers/web/guides/personal-access-tokens and /guides/webhooks-api. Webhooks work under CCG apps. ACL: the collaborations endpoints return full per-file/folder ACLs. [Documented: developer.box.com/guides/authentication/client-credentials/client-credentials-setup]** — _https://developer.box.com/guides/authentication/client-credentials/client-credentials-setup_
  - Implication: Strong BYOT: self-serve creation + own-admin approval, full push, full ACL fidelity. Comparable to Drive/SharePoint as a high-fidelity content source.
- **Dropbox: Scoped app in the customer's own App Console; token generation self-serve (short-lived access tokens + refresh tokens are the norm now); team scopes yield a team access token with Select-User/Select-Admin member impersonation. Webhooks configured on the app notify on content changes. Production approval only matters for multi-user public distribution, not own-team use. ACL: sharing endpoints (list_folder_members etc.) return member lists per shared folder/file. [Documented: dropbox.com/developers/reference/auth-types; dropbox.tech scoped-apps post. Own-team approval exemption: documented in dev guide]** — _https://www.dropbox.com/developers/reference/auth-types_
  - Implication: Full BYOT + push + good ACL reads. SDK must handle refresh-token rotation (no permanent tokens anymore) — same lifecycle plumbing Zendesk now needs.
- **Gong: Access Key + Secret generated by a Technical Administrator in Company Settings > API — pure API-key auth, no OAuth needed (API access is plan-gated on some tiers: inferred). Webhooks: 'Fire webhook' actions on Automation Rules in Admin Center (JWT-signed or token-in-URL), fired per matching call. Rate limits are tight (third-party sources cite ~1k req/hr; Gong docs cite 3 calls/sec / 10k calls/day — verify per contract). ACL: call visibility is governed by Gong permission profiles which are NOT granularly exposed via the API — the key sees what its data-access scope allows. [Documented: help.gong.io create-a-webhook-rule; key creation via Stitchflow/Gong docs. ACL non-exposure: inferred]** — _https://help.gong.io/docs/create-a-webhook-rule_
  - Implication: BYOT + rule-based push work. ACL fidelity is poor — Gong calls should default to quarantine or a coarse admin policy (e.g., 'visible to revenue org'). Rate limits make backfill slow; lean on webhooks.
- **Stripe: Restricted API keys created in the dashboard with per-resource read/write permissions; webhook endpoints creatable via dashboard or API. ACL: not applicable — Stripe data has no per-user ACL model; access is account/key-level. [Documented: Stripe docs on restricted keys and webhook endpoints — stable, well-known surface; not re-verified this session]** — _https://docs.stripe.com/keys_
  - Implication: Trivial BYOT + push. Treat as account-scoped data with a single admin-assigned visibility policy (e.g., finance team).
- **Postgres/MySQL: Database credentials + logical replication slot (Postgres) / binlog (MySQL) — no OAuth concept at all; Verity's existing Debezium ingest path already covers CDC. ACL: SQL GRANTs exist but don't map to document-level ACLs; row data carries no principal metadata unless the schema encodes it. [Documented: standard DB behavior; Verity's Debezium endpoint already built]** — _https://debezium.io/documentation/_
  - Implication: Already solved for auth+CDC. ACL must come from admin-assigned visibility policy or schema-declared principal columns — a good place for a declarative 'ACL mapping' config in the connector SDK.

  - Implication: Verity's ACLs-ride-with-content invariant is fully satisfiable for Tier A (the highest-value content sources), approximable for Tier B, and requires the quarantine/admin-visibility-policy path for Tier C — which validates that path as a core feature, not an edge case.

### Recommendations
1) Make BYOT the default and only auth mode of the Apache-2.0 core: every connector's quickstart is 'create a key/private-app/service-account in YOUR tenant, paste it into Verity' — this achieves the 5-minute wow for all 20 systems with zero vendor OAuth apps, and reserves Merge/Nango strictly for the cloud edition's multi-tenant long tail. 2) Build a credential-lifecycle abstraction in the connector SDK now, not per-connector: {static key | PAT | client_credentials minting | refresh-token rotation}, with expiry telemetry — Zendesk (tokens dead by Apr 2027), Atlassian (scoped tokens + gateway URLs), and Dropbox (short-lived tokens) already require it; assume more vendors follow Zendesk. 3) Solve webhook receivability three ways and let connectors declare which they support: (a) public HTTPS ingest endpoint (Graph, Drive, Asana, GitHub, Airtable, Monday, Zendesk, Box, Stripe), (b) WebSocket/long-poll lane for Socket-Mode-style delivery (Slack today; design it generically), (c) delta/poll fallback for everything (Drive changes.list, Graph delta, Notion search) so no source is push-blocked. 4) Encode the ACL tiers as SDK contract levels: Tier A connectors MUST emit real AclEnvelopes; Tier B emit group/container-membership ACLs with a documented approximation note; Tier C connectors REQUIRE an admin-assigned visibility policy at setup time (refuse to start without one) — this turns the quarantine invariant into an onboarding step rather than a runtime surprise. 5) Prioritize connector build order by (BYOT ease × ACL fidelity × webhook quality): GitHub, Linear, Slack, Box, Google Drive, and Graph/SharePoint are the cleanest wins; Zendesk and Atlassian need the new-auth patterns baked in from day one; Gong and Notion ship with visibility-policy-required flags. 6) Re-verify two fast-moving items before GA docs: HubSpot Service Keys webhook support (beta may add it) and Zendesk migration tooling; also confirm Gong rate limits against a real contract since public numbers conflict.

## ingestion-dx

Across 2026 ingestion tools, "incredibly easy" reduces to five repeatable mechanisms: (1) zero-infrastructure first run (embedded/local defaults: Chroma's 4-line add with a local default embedder, PyAirbyte's automatic DuckDB cache, Turbopuffer's copy-paste quickstart with local BGE embeddings and no external API key); (2) one credential + one call push APIs (Inngest's inngest.send() with a single env-var event key; Estuary's zero-config HTTP Ingest webhook URL that accepts any JSON); (3) drop-a-file endpoints where the server does parsing/chunking/embedding invisibly (OpenAI vector stores, Anthropic Files API, Unstructured's auto file-type routing); (4) piggybacking on free loader ecosystems by shipping one sink integration (Zep and Mem0 became targets for 300+ LlamaIndex readers and 100-200+ LangChain loaders by writing a single VectorStore/Memory class); and (5) agent-driven ingestion — MCP write tools and AI-generated declarative connectors (Airbyte's Connector Builder AI Assistant and connector-builder-mcp let agents author connectors from API docs), which in 2026 is how the long tail gets built without anyone writing OAuth clients. Long-term retention comes not from the entry point but from owned incremental state (cursors, caches, lineage — PyAirbyte caches, CocoIndex's fingerprint/memoization engine, Estuary collections) and from schema/policy registries. For Verity, the highest coverage-per-engineering-hour set is: a generic per-source webhook URL, a verity CLI (file/dir/URL/stdin) with required --visibility for un-ACL'd data, LlamaIndex+LangChain sink packages, a PyAirbyte destination bridge, MCP write tools, and a multipart file-upload endpoint — explicitly NOT building per-source OAuth.

### Findings
- **PyAirbyte collapses 'hundreds of connectors' into a 3-line Python pattern: get_source(name, config) -> source.read(), with connectors installed on demand (declarative YAML manifests fetched from connectors.airbyte.com, Python connectors installed via uv, or docker_image=True) and a zero-setup local DuckDB cache by default. [documented]** — _https://github.com/airbytehq/PyAirbyte/blob/main/README.md ; https://docs.airbyte.com/developers/pyairbyte_
  - Implication: Verity can inherit Airbyte's entire source catalog without building or hosting anything by shipping a small 'Verity cache/destination' for PyAirbyte (or a `verity ingest airbyte:source-hubspot` CLI wrapper). Users supply their own API keys/configs, so Verity never builds OAuth clients. Caveat: Airbyte streams carry no ACLs, so this lane must require an explicit admin-assigned visibility policy or land in quarantine — matching the existing fail-closed invariant.
- **Airbyte's 2026 answer to the long tail is agents writing connectors, not humans: connectors are declarative YAML manifests (low-code CDK covers ~90% of REST APIs), the Connector Builder AI Assistant prefills streams/pagination/incremental cursors from API docs, and connector-builder-mcp gives coding agents ownership of the full lifecycle (manifest validation, automated testing, PR creation). [documented]** — _https://docs.airbyte.com/platform/connector-development/connector-builder-ui/ai-assist ; https://github.com/airbytehq/connector-builder-mcp_
  - Implication: Verity's connector SDK should be manifest-first (declarative YAML/JSON describing endpoints, cursors, and — uniquely — the AclEnvelope mapping) plus an MCP server for connector authoring, so Claude Code/Cursor users can generate a working Verity connector for any REST API in one session. The ACL-mapping section is the one part that should require explicit human confirmation before leaving quarantine.
- **Estuary's HTTP Ingest connector is the cleanest push-lane DX pattern found: it requires no endpoint-specific configuration, mints a unique public URL per capture, accepts any valid JSON from any source (multiple custom paths per capture), validates against the collection's write schema (rejecting the whole request with HTTP 400 on failure), and serializes query params under /_meta/. [documented]** — _https://docs.estuary.dev/reference/Connectors/capture-connectors/http-ingest/_
  - Implication: A 'mint me a webhook URL' primitive is the cheapest way to make ANY system (GitHub, Stripe, Zapier, internal cron jobs) a Verity source with push freshness and zero OAuth. Verity already has POST /v1/episodes and /v1/ingest/debezium; generalizing to per-source scoped webhook URLs with a JSONata/JMESPath-style payload mapping and fail-closed (400/quarantine) validation is directly analogous and preserves the ACL invariant.
- **CocoIndex (Rust core, Python face — architecturally Verity's closest cousin) wins on 'write batch-style code, the engine runs it incrementally': multi-level change detection (component/function/target), memoization, and per-row lineage back to source bytes, with a 5-minute quickstart and no DSL. [documented]** — _https://cocoindex.io/docs/getting_started/overview/_
  - Implication: Validates Verity's Rust+Python split and sets the SDK bar: connector authors should write naive 'fetch everything' code while the truth lane handles diffing, cursors, and bi-temporal facts. Verity's 31ms-to-queryable and byte-level lineage/audit story are directly comparable marketing claims; auditable lineage doubles as an ACL-provenance feature CocoIndex doesn't have.
- **Memory products become sinks for entire loader ecosystems by shipping ONE integration class: Zep and Mem0 each got LlamaIndex (300+ integration packages, SimpleDirectoryReader for any local file type) and LangChain (100-200+ document loaders, community-contributed) support via a single VectorStore/Memory implementation, making every existing reader a de-facto connector for them. [documented pattern; loader counts vary by source]** — _https://www.llamaindex.ai/blog/zep-and-llamaindex-a-vector-store-walkthrough-564edb8c22dc ; https://docs.mem0.ai/integrations/llama-index ; https://docs.langchain.com/oss/javascript/integrations/document_loaders_
  - Implication: Shipping `VerityVectorStore` (LlamaIndex) and a LangChain vector-store/retriever package is roughly two small Python packages of effort and multiplies source coverage by hundreds of loaders Verity never maintains. Because loaders strip source ACLs, the constructor must take a required visibility_policy (or route to quarantine) — make the ACL invariant impossible to silently bypass rather than hoping users read docs.
- **The first-5-minutes converters all remove the embedding-provider dependency and infrastructure: Chroma is 4 lines to indexed-and-queryable with a bundled local all-MiniLM-L6-v2 embedder; Turbopuffer's quickstart is one copy-paste program (write + vector + FTS + regex query) and explicitly offers 'local embeddings with BGE — no API key needed'; PyAirbyte defaults to in-process DuckDB. [documented]** — _https://docs.trychroma.com/docs/embeddings/embedding-functions ; https://turbopuffer.com/docs/quickstart_
  - Implication: Verity's local embedding is the right default — the 5-minute wow should require exactly one credential (a Verity scope handle) and zero third-party keys. Every docs page should lead with a single copy-paste block that goes from empty to a permission-filtered query result, ideally against an embedded/dev-mode server (`verity dev`).
- **Push-event DX has standardized on 'one env var + one function call': Inngest's inngest.send() needs only INNGEST_EVENT_KEY, batches up to 512KB per request, and gives compile-time typed events; Supabase Database Webhooks are a dashboard-or-SQL wrapper around pg_net triggers that POST row changes on INSERT/UPDATE/DELETE without blocking the database. [documented]** — _https://www.inngest.com/docs/events ; https://supabase.com/docs/guides/database/webhooks_
  - Implication: Verity should ship a typed one-liner (`verity.send(episode)` / `verity.send_fact(...)`) in Python and TypeScript, plus a documented copy-paste Postgres trigger snippet (pg_net -> Verity webhook URL) that gives every Postgres/Supabase user CDC-lite push freshness without deploying Debezium — a much lower on-ramp to the existing Debezium truth lane.
- **'Drop a file, we do the rest' is table stakes: OpenAI's vector stores are upload-file -> attach -> queryable with chunking/embedding/indexing fully hidden (developers accept losing chunking control for zero pipeline); Anthropic's Files API is create-once-use-many (file_id, 100GB/org); Unstructured auto-detects file type and routes pages to the optimal partition strategy (fast/hi-res/VLM/auto) behind one API. [documented]** — _https://developers.openai.com/api/docs/guides/tools-file-search ; https://platform.claude.com/docs/en/build-with-claude/files ; https://github.com/Unstructured-IO/unstructured_
  - Implication: Verity needs a multipart POST /v1/files (or `verity add report.pdf`) that accepts any common format and does parse->chunk->embed server-side. Don't build parsing: embed the Apache-2.0 `unstructured` library (license-compatible with the OSS core) or accept pre-parsed markdown/JSON, and expose chunking overrides later for power users.
- **Agent-driven ingestion via MCP is now a first-class entry point, not a gimmick: mem0/OpenMemory, Cognee (add_tool/search_tool), and Letta all expose memory WRITE operations as MCP tools consumed by Claude Desktop/Cursor/VS Code, and 2026 benchmark commentary favors tool-based memory (agents calling memory beat agents fed by it); Airbyte likewise runs pipelines through MCP. [documented trend; benchmark figures are vendor-published]** — _https://usewire.io/blog/memory-as-tools-2026-agent-memory-pattern/ ; https://docs.airbyte.com/developers/mcp-servers_
  - Implication: Verity's existing MCP server should grow write-side tools — remember/ingest_text, ingest_file, ingest_url — with the scope handle enforcing who may write and a required visibility parameter. This makes the agent itself the universal connector: 'paste this MCP config into Claude, tell it to save your docs' is a credible 5-minute wow that requires zero connectors.
- **Long-term retention/lock-in in these tools comes from owned incremental state and destinations, not from the loaders: PyAirbyte's value compounds in its caches, CocoIndex's in its fingerprint/memoization state, Estuary's in its collections; loaders and entry points are commoditized and interchangeable. [inference from documented architectures]** — _Synthesis across https://github.com/airbytehq/PyAirbyte ; https://cocoindex.io/docs/getting_started/overview/ ; https://docs.estuary.dev/concepts/captures/_
  - Implication: Verity should treat entry points as cheap, numerous, and disposable, and concentrate durable value in what only Verity has: the bi-temporal fact store, per-source cursors, and — uniquely — the ACL/visibility policy registry. Once a team has encoded its permission mappings and sync state in Verity, switching cost is real; no competitor in this survey carries ACLs with content, which is the defensible layer.

### Recommendations
Minimal entry-point set, ranked by source-coverage-per-engineering-hour (each item reuses the existing push lane, quarantine, and scope-handle machinery):

1. Generic scoped webhook URLs (est. days, infinite long-tail coverage). Generalize POST /v1/episodes into 'mint a webhook URL per source' à la Estuary HTTP Ingest: zero config, accepts any JSON, optional JMESPath-style payload mapping, schema/ACL validation fail-closed (400 + quarantine). Ship a copy-paste Supabase/Postgres pg_net trigger snippet as the CDC-lite on-ramp to the Debezium lane. This is the push-freshness answer for every system Verity will never build a connector for.

2. `verity` CLI with four verbs of one command (est. 1-2 weeks). `verity add file.pdf | ./dir | https://url --crawl | -` (stdin pipe), plus `verity dev` for an embedded local server with local embeddings. Exactly one credential (scope handle), no third-party keys. Make `--visibility <policy>` REQUIRED for all un-ACL'd input — the invariant should be enforced by the argument parser, not the docs. This is the 5-minute wow: install -> verity dev -> verity add ./docs --visibility org -> query from Claude via MCP.

3. Framework sinks (est. ~1 week each): `VerityVectorStore` for LlamaIndex and a LangChain vector-store/retriever package. This is the proven Zep/Mem0 move that converts 300+ LlamaHub readers and 100-200+ LangChain loaders into free Verity connectors. Required visibility_policy constructor arg; unmapped -> quarantine.

4. MCP write tools on the existing server (est. days): ingest_text/remember, ingest_file, ingest_url, with scope-handle-gated writes and required visibility. Also publish a declarative connector manifest format (endpoints + cursors + AclEnvelope mapping) and a connector-authoring MCP so coding agents generate long-tail connectors Airbyte-style; require human sign-off only on the ACL-mapping block.

5. PyAirbyte bridge (est. 1-2 weeks): a Verity destination/cache class so `get_source(anything) -> verity_cache` works. Inherits Airbyte's full catalog with user-supplied credentials — Verity builds zero OAuth. Route through the same required-visibility gate.

6. Files upload endpoint (est. ~1 week): multipart POST /v1/files doing parse->chunk->embed server-side via the Apache-2.0 `unstructured` library; mirrors the OpenAI/Anthropic drop-a-file pattern developers already know.

Explicitly do NOT build: per-source OAuth clients (keep Nango optional and Merge cloud-only as specced), a no-code connector-builder UI (let agents + manifests cover it), or your own document parsers. Do NOT position the framework sinks or CLI as the trust path — docs should consistently present two lanes: 'convenience lane' (CLI/sinks/MCP/webhooks, admin-assigned visibility) and 'truth lane' (native + Debezium connectors, source-fidelity ACLs). Sequencing for the founder question: items 1, 2, and 4 first — together they let any developer get any data in within five minutes with no Merge account and no OAuth work by anyone.

## auth-layers

Mid-2026 landscape: there is no fully-OSS turnkey that gives self-hosted users OAuth to Google/Slack/HubSpot with zero app registration. Nango (ELv2) free self-hosted now covers exactly the two things Verity needs — OAuth/auth flows + credential refresh + authenticated proxy for ~800 APIs — but NOT webhooks, syncs/functions, or its MCP server (those are Nango Cloud / paid Enterprise self-host). Composio AgentAuth and Arcade.dev are managed/closed backends (MIT SDKs only; full self-host is enterprise-contract-gated), and Merge/Paragon are closed SaaS — all four are cloud-edition material, not OSS-core material. The rclone "shared OAuth app" pattern (one client_id+secret shipped in the binary) is real, vendor-tolerated to varying degrees, and legally fine (Google's own docs treat installed-app client secrets as non-secret), but it has hard costs: a shared per-client_id QPS quota (rclone users get ~2 files/sec), Google restricted-scope verification + annual CASA audit for full-Drive scope, HubSpot's 25-install cap on unlisted public apps, and a redirect-URI problem that forces the OSS vendor to run a small hosted callback relay anyway. The escape hatches that make a <10-minute self-hosted connect possible without any OAuth app: HubSpot private-app tokens (no OAuth at all), Slack app-from-manifest (2-minute wizard, unlisted distribution needs no review, tokens don't expire by default), and Google service-account + domain-wide delegation or a guided "internal app" (internal Workspace apps skip verification and CASA entirely). Google's device-code flow is a dead end for Verity (only drive.file/drive.appdata allowed, not full drive). MCP's Nov-2025 spec made Client ID Metadata Documents (CIMD) the default client-identity mechanism with DCR as fallback — the right pattern for Verity's own MCP surface, but irrelevant for legacy SaaS OAuth (Google/Slack/HubSpot don't consume CIMD). Recommended architecture: a three-lane "connection ladder" — (1) token-paste/manifest lane in the Apache-2.0 core (HubSpot private apps, Slack manifests, PATs, Google service-account JSON) as the 5-minute wow; (2) bundled/optional Nango self-hosted for developers who register their own OAuth apps, plus copy-paste per-provider app-creation wizards; (3) a free Verity-hosted "OAuth concierge" that owns the verified shared apps (Google CASA'd, Slack unlisted-distributed, HubSpot marketplace-listed) and hands refresh tokens down to self-hosted instances Tailscale-style. Merge long-tail, the CASA-verified shared Google app at scale, and marketplace-listed apps stay cloud-only.

- **Nango free self-hosted (ELv2) covers Auth + Proxy only: managed OAuth flows, API-key auth, token refresh, and the credential-injecting proxy for ~800 APIs, with observability limited to auth+proxy. Functions/syncs, webhooks, the MCP server, custom auth branding, RBAC, SAML, and OTel export are excluded — they require Nango Cloud or a paid Enterprise self-host license (fixed annual fee). One secondary source reports the free self-hosted tier was expanded to ~1,000 connections; the official docs state no explicit connection limit. Both are at most cloud-edition conveniences, and Verity already has Merge for the cloud long-tail. Paragon and Merge are similarly closed SaaS (contrast case): fine for CLOUD, structurally unavailable to OSS users.
- **The rclone shared-OAuth-app pattern is documented and vendor-tolerated but has sharp edges: rclone ships one Google client_id/secret used 'by all users of rclone across the world'; Google rate-limits per client_id (~10 QPS default), so shared-app users get ~2 files/sec and are told to create their own client_id for real use. Google's installed-app docs treat the embedded client_secret as non-secret, so shipping it is practically and ToS-tolerated. A user creating their OWN Google OAuth app for personal use can stay unverified (scary consent screen, 100-user cap for sensitive/restricted scopes, 7-day refresh-token expiry while in 'Testing' — fixed by publishing without verifying). But an app DISTRIBUTED at scale using restricted scopes (full drive / drive.readonly) requires Google restricted-scope verification plus an annual CASA security assessment by an approved lab (typical cost hundreds to a few thousand dollars/yr at Tier 2 via Google's discounted TAC Security rate; more for higher tiers). [Documented: rclone.org/drive, Google identity docs, deepstrike.io CASA 2025 breakdown]** — _https://rclone.org/drive/ ; https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification ; https://deepstrike.io/blog/google-casa-security-assessment-2025 ; https://forum.rclone.org/t/oauth-verification-after-october-3-2022/32809_
  - Implication: Verity CAN ship a shared Google OAuth app rclone-style, but only the hosted cloud entity should own it: it must be verified + CASA-audited annually (a real but affordable recurring cost for a funded team), and the shared per-client_id quota means it's a great '5-minute wow' onramp and a bad permanent transport — the product should nudge heavy self-hosted users to their own app (or domain-wide delegation) after trial. Crucially, full-Drive ACL-fidelity ingest requires a restricted scope, so there is no CASA-free shared-app path for Google.

Slack: 'unlisted public distribution' is an official, review-free path — activate it, get a shareable install URL / Add-to-Slack button installable on unlimited workspaces; Marketplace review is only for listing; bot tokens don't expire by default. HubSpot: public apps installable via OAuth install URL without marketplace listing, but hard-capped at 25 installs until HubSpot Ecosystem Quality review + listing (then unlimited); unverified apps show a warning banner. Google: see CASA finding. Also, Google's device-code flow (the natural CLI pattern) supports only a short allowed-scope list — drive.file and drive.appdata but NOT full drive — so device flow cannot power whole-corpus Drive ingest. [All documented from vendor docs]** — _https://docs.slack.dev/app-management/distribution/ ; https://api.slack.com/start/distributing/public ; https://developers.hubspot.com/docs/apps/developer-platform/build-apps/manage-apps-in-hubspot ; https://eshopman.com/blog/development-integrations/navigating-hubspots-app-install-limits-a-guide-for-unlisted-public-apps/ ; https://developers.google.com/identity/protocols/oauth2/limited-input-device_
  - Implication: A single shared-app strategy across providers doesn't exist; it's per-vendor. Slack shared app: cheap and legitimate — do it. HubSpot shared app: requires getting through marketplace review (Verity has a native HubSpot connector anyway, and HubSpot's marketplace listing is itself distribution). Google: gated by CASA and quota. And the CLI device-flow shortcut is off the table for Drive, which pushes Verity toward either a hosted redirect relay for browser OAuth or non-OAuth credentials (service accounts, private-app tokens).
- **The zero-OAuth-app escape hatches are the fastest real path to <10-minute connects for self-hosters: HubSpot 'private apps' issue a static access token per portal with admin-chosen scopes — no OAuth app, no review, ~2 minutes. Slack 'create app from manifest' spins up a workspace app (Verity ships the manifest JSON; user clicks through, installs, copies bot token) in ~2-3 minutes with no distribution/review needed for one's own workspace. Google Workspace: a service account with domain-wide delegation (admin pastes client ID + scopes in Admin console, uploads JSON key) needs no OAuth consent flow, no verification, no CASA, and is the ONLY practical way to impersonate all users for whole-domain Drive ingest with ACL fidelity anyway; alternatively a customer-created 'internal' OAuth app skips verification entirely. [Documented vendor mechanisms; the '<10 minutes' timing is inference from the documented step counts]** — _https://developers.hubspot.com/docs (private apps) ; https://docs.slack.dev (app manifests) — mechanism details are stable documented vendor features; timings inferred_
  - Implication: Verity's OSS core should make 'paste a credential' the first-class lane, not a fallback: for the flagship connectors, per-provider guided wizards (deep-link into the vendor console, ship the Slack manifest, ship the exact HubSpot scope list, ship the DWD scope string) get a developer connected without Verity building or hosting ANY OAuth machinery. This also aligns with the ACL invariant — service-account/DWD and bot-token models see org-level permission metadata that per-user OAuth grants often can't.
- **MCP-ecosystem auth converged in the 2025-11-25 spec: MCP servers must implement OAuth 2.0 Protected Resource Metadata (RFC 9728) for AS discovery; Client ID Metadata Documents (CIMD, draft-ietf-oauth-client-id-metadata-document) became the DEFAULT client-identity mechanism — the client's client_id is a URL hosting its metadata JSON, fetched and validated on the fly with no stored registration — with Dynamic Client Registration (RFC 7591) demoted to fallback. mcp-remote-style bridges (local stdio client to remote MCP server, handling the OAuth dance in-browser) remain the standard shim for clients without native remote-OAuth support. Keycloak, as the generic-OSS-broker option, shipped standard token exchange GA in 26.2 (May 2025) and by 26.5-26.7 (2026) supports exchanging a realm token for an EXTERNAL IdP token via a dedicated endpoint, plus JWT authorization grant and experimental delegation scopes — but its external-token support covers OAuth/OIDC social providers generically, and it does not manage provider-specific scopes, app registration, or API quirks. [Documented: modelcontextprotocol.io spec, keycloak.org release posts]** — _https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization ; https://www.keycloak.org/2025/05/standard-token-exchange-kc-26-2 ; https://www.keycloak.org/2026/01/jwt-authorization-grant ; https://workos.com/blog/dynamic-client-registration-dcr-mcp-oauth_
  - Implication: Two takeaways for Verity. (a) For Verity's OWN MCP server, adopt RFC 9728 + CIMD now — any MCP client can connect to a self-hosted Verity with zero pre-registration, which IS the ecosystem's answer to 'auth without registering apps' for the agent-facing side. (b) Keycloak-style brokers solve identity federation, not third-party API credential management — you'd still register a Google/Slack/HubSpot app per deployment and get none of Nango's per-provider refresh/quirk handling, so Keycloak is the wrong tool for the ingest-side problem (documented capabilities; 'wrong tool' judgment is inference).
- **The shared-app pattern has a structural redirect-URI problem for self-hosted software: OAuth callbacks must land on a URL pre-registered on the shared app, which a random self-hosted instance's domain never is. rclone dodges this because Google installed-app clients allow localhost loopback redirects, but Slack requires HTTPS redirect URLs and HubSpot/Slack web apps can't enumerate customer domains — so any shared-app scheme for web-based providers forces the vendor to run a small hosted callback relay that forwards the authorization code (via state) to the local instance, and PKCE support to protect that relay is inconsistent across these providers. [Redirect-registration requirements documented per vendor; the relay-architecture consequence is inference from those requirements, matching how Nango Cloud and similar products actually work]** — _Vendor OAuth docs (Slack/HubSpot redirect requirements, Google loopback for installed apps); architecture conclusion labeled inference_
  - Implication: Even the most OSS-purist shared-app design drags a thin Verity-hosted service into existence. Better to embrace it deliberately as a free 'OAuth concierge': Verity Cloud hosts the verified shared apps and the callback relay, then hands the resulting refresh token DOWN to the self-hosted instance (Tailscale login-service model) so tokens live on customer infrastructure and the concierge stores nothing. This keeps the Apache-2.0 core fully functional without the concierge (via lane 1/2) while making the concierge the frictionless default.

### Recommendations
Build a three-lane "connection ladder," in this priority order:

LANE 1 — Zero-OAuth credential wizards in the Apache-2.0 core (build first; this is the 5-minute wow). Per-provider guided setup that never touches OAuth apps: HubSpot private-app token (ship the exact scope list, ~2 min); Slack app-from-manifest (ship the manifest JSON with the scopes Verity's connector needs, user installs to own workspace, pastes bot token, ~3 min); Google service account + domain-wide delegation for Workspace (ship the scope string and an admin-console deep link) — DWD is also the only credential shape that supports whole-domain, ACL-faithful Drive ingest, so it's required for the truth lane regardless; generic PAT/API-key lane for everything else. `verity connect slack` opens the browser to the right console page, validates the pasted credential, and confirms ACL mappability before ingest (fail-closed quarantine preserved).

LANE 2 — Bring-your-own OAuth app via bundled Nango self-hosted (optional docker-compose profile). Confirm the ELv2 posture with counsel (internal use behind your product is generally fine; don't resell Nango itself as the service), and rely on it only for what its free self-hosted tier actually covers — OAuth flows, token refresh, credential-injecting proxy. Verity's native connectors keep owning webhooks/push and ACL retrieval, so Nango's excluded features don't matter. Pair with per-provider "create your own OAuth app in 10 minutes" wizards (rclone-style docs, but automated): for Google, walk users to an INTERNAL Workspace app (no verification, no CASA) or a published-unverified personal app with the scary-screen caveat documented honestly.

LANE 3 — Verity-hosted free "OAuth concierge" (thin cloud service, ships later): Verity registers and maintains ONE verified app per flagship provider — Slack via unlisted public distribution (review-free, unlimited workspaces), HubSpot via marketplace listing (budget for Ecosystem Quality review; the 25-install cap makes unlisted-shared-app a non-starter), Google via restricted-scope verification + annual CASA Tier 2 (budget low-thousands USD/yr). The concierge hosts only the redirect/callback relay and hands refresh tokens down to the self-hosted instance, storing nothing — sovereignty preserved, and the OSS core remains fully usable if the concierge disappears. Surface Google's shared-quota reality in-product (rclone's lesson): after trial-scale usage, prompt migration to Lane 1 (DWD) or Lane 2.

Cloud-only: Merge long-tail connectors (SaaS contract), the CASA-verified shared Google app at production scale, marketplace-listed apps, and any Composio/Arcade-style managed toolauth (both are closed-backend and enterprise-gated for self-host — do not put them in the OSS path). Skip Keycloak for the ingest side: token exchange GA (26.2) and external-IdP token retrieval (26.5+) solve identity federation, not third-party API credential lifecycle.

For Verity's own MCP server, implement the 2025-11-25 MCP auth spec now: RFC 9728 Protected Resource Metadata plus CIMD (URL-as-client_id) with DCR fallback — that gives any MCP client zero-registration connection to a self-hosted Verity, which is the agent-side mirror of the same "no app registration" goal.

Explicitly avoid: Google device-code flow for Drive (full drive scope not on the allowed list — only drive.file/appdata), shipping a shared Google client_id in the OSS binary as the primary path (shared ~10 QPS quota + CASA obligations land on you while quota pain lands on users), and any design where self-hosted tokens rest in a third-party cloud.

## mapping-dsl

Declarative "config-file connector" ingestion is a proven, mainstream pattern by mid-2026, and the strongest prior art maps almost 1:1 onto Verity's proposed generic POST /v1/ingest/webhook + YAML source manifest. Airbyte's declarative low-code CDK demonstrates that ~80% of REST-API source connectors can be pure YAML config (auth, streams, pagination, record selection, incremental cursors, error handling), executed by a generic interpreter with an escape hatch to custom code. LLM-authored manifests are shipped production reality, not speculation: Airbyte's AI Assistant (with Fractional AI, since Sept 2024) drafts connector manifests from API docs, and Superglue (YC W25, open source) has an LLM generate API configs plus JSONata mappings and then validates the generated mapping against the user's target schema with self-healing on drift — establishing the "LLM drafts, deterministic conformance harness verifies, human approves" loop. On mapping language, JSONata has emerged as the de-facto declarative JSON-to-JSON transform standard (adopted by AWS Step Functions Nov 2024; Superglue's LLM target language), while CEL is the standard for predicates/policy (filters, routing conditions) rather than document reshaping, and jq/JS code steps are the universal escape hatch (Zapier/n8n/Pipedream/Hookdeck/Convoy all converge on expression-or-code for nontrivial transforms). The one thing with essentially no prior art is Verity's hard invariant: no declarative connector framework today carries ACLs in the manifest — Glean's push Indexing API (documents pushed with permissions attached, datasource-level identity config) is the closest analogue, and it is imperative code, not config. That gap is Verity's differentiation opportunity and its highest-severity failure mode: an LLM must never be allowed to default the ACL block.

  - Implication: Verity's webhook lane should be: declarative filter (predicate) + declarative mapping (JSONata) as the default path, with the existing Python SDK as the code escape hatch — and should copy the constraint discipline (timeouts, no network/imports in transforms) because everyone who ships user-supplied transforms bounds them hard.
- **Debezium SMTs show config-driven transformation with two useful idioms Verity already touches: (1) predicate-gated transforms (apply this SMT only to events matching a predicate) and (2) convention-over-configuration (outbox EventRouter assumes fixed column names id/aggregatetype/aggregateid/type/payload and works with zero config if you follow the convention). - **Singer is the cautionary tale: a good wire protocol (JSONL RECORD/SCHEMA/STATE streams; config/catalog/state file separation; Meltano SDK's state partitioning for per-partition bookmarks) but taps are imperative Python code, and the ecosystem became a long tail of inconsistently maintained connectors; Meltano's SDK reduces boilerplate but never made taps declarative. Do steal Singer/Meltano's state design (opaque per-stream, per-partition cursor state echoed back by the platform) for the poll lane.
- **The closest prior art for ACLs-ride-with-content ingestion is Glean's Indexing (Push) API: a configured 'datasource' with identity settings (isUserReferencedByEmail vs datasourceUserId), and documents pushed with per-document permissions objects; sample connectors are imperative code against that API. No declarative connector framework surveyed (Airbyte, Singer, Benthos/Redpanda Connect, Superglue) has any ACL concept in its manifest.   - Implication: The acl_policy block must be structurally excluded from LLM authoring defaults: no implicit default visibility, enum-constrained modes only, explicit human/admin approval gate before a manifest activates, and quarantine as the absent-block behavior.

### Recommendations
1) Build exactly the proposed primitive: a generic POST /v1/ingest/webhook endpoint plus a YAML "source manifest," and treat the manifest as the product. Model the manifest schema on Airbyte's declarative component taxonomy, which is the proven vocabulary: `source` (name, auth ref pointing at a stored secret — never inline credentials; webhook signature verification scheme: HMAC-SHA256 header name + secret ref), `entities[]` (entity type, primary-key expression, event routing: predicate on event_type/topic -> operation create|update|delete, field mappings, valid-from/observed-at timestamp extraction for bi-temporality), `poll` (optional truth-lane: endpoint, Airbyte-style paginator + cursor with opaque server-echoed state à la Singer/Meltano, request interpolation), and a REQUIRED `acl_policy` block. One manifest should serve both lanes (webhook = freshness, poll = reconciliation backstop for lost deliveries).

2) Mapping language: adopt JSONata as the declarative mapping dialect (LLM-friendly, Step Functions-mainstream, transformation-complete, schema-checkable as Superglue proved), but run a 1-week spike on Rust evaluator maturity first; the fallback is a Verity-defined JSONata subset (paths, object construction, a whitelisted function set) or the reference implementation in a WASM sandbox. Either way enforce hard evaluation limits (time, depth, output size) since JSONata allows recursion. Use CEL-style predicates only for filters/event routing if JSONata predicates prove awkward — do not use CEL for field mapping. Keep the existing Python SDK as the documented escape hatch for the ~20% of sources that config cannot express (Airbyte's manifest-only share suggests ~80% coverage).

3) Make `acl_policy` a first-class, enum-constrained, human-gated block with exactly three modes matching the existing invariant: `map` (JSONata/path expressions extracting principals from the payload, with a declared identity namespace — copy Glean's isUserReferencedByEmail vs native-user-id distinction), `static` (explicit admin-assigned visibility policy by reference), and `quarantine` (the default when the block is absent or mapping fails at runtime — fail closed). Require an explicit admin approval step to activate any manifest whose acl_policy is `map` or `static`, and never let the LLM authoring flow emit a default visibility.

4) Ship the conformance harness with the manifest format, not after it: manifests embed `fixtures[]` (sample webhook payloads / recorded API responses + expected emitted facts and ACL envelopes), and a `verity manifest test` CLI runs them locally and in CI. This is the Superglue validation loop plus Airbyte's benchmark-against-known-connectors practice, and it is what makes LLM authoring safe: the flow is "point LLM at API docs -> draft manifest -> auto-generate/run fixtures -> deterministic pass/fail -> human approves acl_policy -> activate." Add drift detection in production (mapping failure rate, unexpected-field rate) that degrades to quarantine rather than dropping or mis-filing records.

5) Exploit that manifests are data, not code: host a community manifest registry (plain YAML files, reviewable diffs, no supply-chain code execution — a real advantage over Singer's imperative tap ecosystem for an Apache-2.0 project), and ship convention-over-configuration defaults (a documented Verity-native webhook shape that needs zero mapping, Debezium-outbox-style) so the 5-minute wow for a well-behaved source is: create secret, paste 15-line manifest (or let the LLM draft it), curl a sample payload, see the fact queryable. This answers the founder's question directly: developers without a Merge account get any REST/webhook source via a config file and their own credentials, with no OAuth client work by Verity (Nango remains the optional OAuth layer, referenced from the manifest's auth ref).
