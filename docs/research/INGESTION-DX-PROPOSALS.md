# Ingestion DX — Proposals & Judge Verdict

## The Loading Dock — an inbound-only ingestion plane for Verity (push-first minimalism) (push-first)

**Thesis:** Verity should stop thinking of ingestion as "we connect to your systems" and invert it: your systems connect to Verity. Every surveyed system (20/20, PAT-COVERAGE) lets the customer self-provision a first-party credential, and ~18/20 can push events under it — so the auth problem is already solved on the developer's side of the wire. Verity therefore ships only receiving surfaces: one canonical write envelope, minted scoped webhook URLs (Estuary HTTP-Ingest pattern), a CLI, MCP write tools, a file-drop endpoint, and framework sinks — and zero vendor-hosted OAuth apps in the Apache-2.0 core. The single credential a developer ever needs from us is a Verity scope handle (HMAC, already built); the single hard gate at every door is the ACL invariant: no write is accepted without either a real AclEnvelope or an explicitly admin-assigned visibility policy, enforced structurally in the Rust write path (fail-closed quarantine), not in docs. Merge stays cloud-only; Nango stays an optional BYO-OAuth-app profile; the flagship native connectors (Drive, SharePoint, Salesforce, Slack, HubSpot, Debezium) remain the "truth lane" for Tier-A ACL fidelity — the Loading Dock is how the entire long tail gets in without anyone (us or them) registering an OAuth app. Durable value concentrates where the research says lock-in actually lives: the bi-temporal fact store, per-source cursors, and the visibility-policy/ACL registry — entry points are deliberately cheap, numerous, and disposable.

**Entry Points:** Ranked by funnel order (what a developer meets first → last), each reusing the existing push lane, scope handles, and quarantine:

1. POST /v1/episodes + POST /v1/facts with the canonical Verity envelope — the curl-in-60-seconds surface. One header (scope handle), one JSON body, `visibility` field required when no acl block present; 400 + quarantine otherwise. Already 80% built.

2. `verity` CLI (new): `verity dev` (embedded server, local embeddings, prints scope handle); `verity add <file|dir|url|->` with `--visibility` REQUIRED by the argument parser for un-ACL'd input; `verity mcp install <client>`; `verity webhook mint <name>`.

3. Minted scoped webhook URLs — generalize /v1/episodes à la Estuary HTTP Ingest: `verity webhook mint github --visibility eng` returns a unique URL that accepts any JSON, verifies HMAC signatures (per-provider scheme declared at mint), and applies an optional JSONata mapping. A documented Verity-native payload shape needs zero mapping (Debezium-outbox-style convention over configuration). This is the push-freshness answer for every source we will never build a connector for, including Zapier/n8n/cron jobs/internal services.

4. MCP write tools on the existing server: `remember`/`ingest_text`, `ingest_file`, `ingest_url` — scope-handle-gated, required `visibility` param. The agent itself becomes the universal connector ("paste this MCP config into Claude, tell it to save your docs").

5. Multipart POST /v1/files: drop-a-file, server does parse→chunk→embed via the Apache-2.0 `unstructured` library (we build no parsers). Mirrors the OpenAI/Anthropic pattern developers already know.

6. Framework sinks: `VerityVectorStore` (LlamaIndex) + LangChain vector-store/retriever package — the proven Zep/Mem0 move that turns 300+ LlamaHub readers and 100–200+ LangChain loaders into free connectors. `visibility_policy` is a required constructor argument.

7. CDC-lite: copy-paste Supabase/Postgres pg_net trigger snippet POSTing row changes to a minted webhook URL — the low-friction on-ramp to the already-built Debezium truth lane.

8. Declarative source manifests (YAML) layered on the webhook endpoint: auth ref (secret store, never inline), event routing predicates, JSONata field mappings, bi-temporal timestamp extraction, optional poll/reconciliation block with Singer/Meltano-style opaque echoed cursor state, embedded `fixtures[]` run by `verity manifest test`, and a mandatory human-gated `acl_policy` block. Manifests are data, not code — reviewable, diffable, registry-hostable, LLM-draftable (Airbyte AI Assistant / Superglue playbook: LLM drafts, deterministic fixtures verify, human approves the ACL block).

Sequencing: 1–4 first (the founder-question answer), then 5–6, then 7–8. Explicitly NOT built: per-source OAuth clients, a no-code builder UI, our own document parsers, or a PyAirbyte bridge in v1 (defer; it's a backfill convenience, not a push surface).

**Auth Story:** Two halves, both Merge-free.

Verity-side (the only credential we issue): the existing HMAC scope handle. It authenticates the WRITER and carries a visibility ceiling — a handle minted for the "github-eng" webhook can never write facts visible beyond eng. `verity dev` prints one on first run; that is the entire credential story for the 5-minute wow (local embeddings mean zero third-party keys).

Source-side (BYOT, verified across 20/20 systems): the developer self-provisions a first-party credential in THEIR tenant — HubSpot private app (~2 min), Slack app-from-manifest with Socket Mode (~3 min, no public endpoint, no review), Google service account + domain-wide delegation (the only credential shape that supports whole-domain ACL-faithful Drive ingest anyway), Entra app registration with Sites.Selected, fine-grained GitHub PATs or customer-created GitHub Apps, and customer-created OAuth clients with client_credentials where vendors mandate it (Zendesk 2026–27, Salesforce post-Sept-2025, Box CCG). Under the push-first lens, for most long-tail sources Verity never even stores that credential: `verity connect github` uses the pasted PAT once, from the developer's machine, to programmatically register a webhook pointing at the minted URL, then keeps it only if the manifest declares a reconciliation poll. Where credentials are retained (truth-lane connectors, poll backstops), one SDK-level credential-lifecycle abstraction handles all four shapes — {static key | PAT | client_credentials minting | refresh-token rotation} — with expiry telemetry, because Zendesk, Atlassian, and Dropbox already require it and more vendors will follow.

Webhook receivability solved three ways, declared per source: (a) public HTTPS ingest endpoint; (b) a generic WebSocket/long-poll lane (Slack Socket Mode today, designed generically so firewalled self-hosters aren't push-blocked); (c) delta/poll fallback (Drive changes.list, Graph delta) so no source is dead-ended. Nango self-hosted (ELv2, free tier covers exactly OAuth flows + refresh + proxy) ships as an optional docker-compose profile for developers who insist on browser-OAuth with their own registered app — pending the counsel review the research flags. Merge, marketplace-listed shared apps, and any CASA-verified shared Google app remain strictly cloud-edition. For Verity's own MCP server: implement the 2025-11-25 spec (RFC 9728 Protected Resource Metadata + CIMD, DCR fallback) so any MCP client connects to a self-hosted Verity with zero pre-registration — the agent-side mirror of the same no-app-registration goal.

**Acl Story:** One structural rule at a single choke point: the Rust write path accepts a fact only if it carries exactly one of {a real AclEnvelope, a reference to an admin-assigned visibility policy}; anything else is quarantined (or 400 in strict/sync mode). No SDK, sink, or endpoint can bypass it, so the invariant survives every entry point by construction, not convention. Per surface:

— curl / raw API: `visibility` field or acl block required in the envelope; absent → quarantine.
— Minted webhook URLs: visibility policy is bound AT MINT TIME into the URL's scope handle by an admin — the pusher's payload can narrow visibility but never widen it. Wrong-policy blast radius is one URL, revocable instantly.
— CLI: `--visibility` enforced by the argument parser for all un-ACL'd input (files, dirs, URLs, stdin).
— MCP write tools: required `visibility` parameter, capped by the scope handle's ceiling.
— Files endpoint: required form field. Framework sinks: required constructor argument (loaders strip source ACLs, so this lane is always policy-based).
— Manifests: a mandatory, enum-constrained `acl_policy` block with exactly three modes — `map` (JSONata expressions extracting principals, with declared identity namespace à la Glean's email-vs-native-id), `static` (policy by reference), `quarantine` (the default when absent or when mapping fails at runtime). Activation of any `map`/`static` manifest requires explicit admin approval, and the LLM-authoring flow is structurally forbidden from emitting a default visibility — this is the highest-severity failure mode in the whole design (a wrong ACL block leaks permissions into shared agent memory, invisibly) and no surveyed product has a playbook for it, so we gate it with humans + fixtures.
— Truth lane: ACL tiers become SDK contract levels. Tier A (Drive, SharePoint/Graph, Box, Dropbox, GitHub, Jira/Confluence, Salesforce) MUST emit real AclEnvelopes from source permission APIs; Tier B (Slack channels, Front inboxes, Linear teams, Monday boards, Zendesk groups) emit container-membership ACLs with a documented approximation note; Tier C (Notion, Gong, Intercom, HubSpot CRM, Stripe, raw DBs) REQUIRE a visibility policy at setup and refuse to start without one — turning quarantine from a runtime surprise into an onboarding step. Runtime drift detection (mapping-failure and unexpected-field rates) degrades to quarantine, never to mis-filing.

Honest limit of the lens: pushed payloads rarely carry source ACLs, so the Loading Dock leans on admin visibility policies for the long tail; genuine per-object ACL fidelity comes only from the Tier-A native connectors pulling permission APIs. That is the intended division of labor — convenience lane vs truth lane — and docs must present it as two explicitly labeled lanes, never blurred.

**Five Minute Wow:** 0:00 — `curl -sSL install.verity.dev | sh` (single static Rust binary + Python extras lazily fetched).
0:30 — `verity dev` → embedded server on localhost:7777 with bundled local embeddings, prints a scope handle and three copy-paste next steps. Zero third-party keys, zero docker, zero config.
1:00 — Paste the printed curl: `curl -X POST localhost:7777/v1/episodes -H "Authorization: Verity vk_dev_…" -d '{"text":"Acme renewal is at risk; champion left in June","visibility":"org"}'` → returns a fact ID; `verity query "acme risk"` shows it queryable (~31ms, the existing benchmark).
1:30 — `verity add ./docs --visibility org` → parses, chunks, embeds a real directory locally; progress bar shows facts landing. Try omitting `--visibility`: the CLI refuses with a one-line explanation of the ACL invariant — the invariant IS the onboarding lesson.
3:00 — `verity mcp install claude` writes the MCP config; in Claude: "what do we know about the Acme renewal?" → permission-filtered answer with per-fact lineage. Then, from Claude: "remember that legal signed off on the Acme MSA" → the agent writes back through the MCP `remember` tool. Memory is now bidirectional.
4:00 — `verity webhook mint stripe --visibility finance` → prints a URL; paste it into the Stripe dashboard's webhook settings (developer's own restricted key, their tenant, no OAuth anywhere). Trigger a test event; `verity tail` shows it land as a fact within a second.
5:00 — Done: files, agent memory, and a live push feed from a real SaaS system, one credential total, no Merge, no OAuth app registered by anyone. The docs page is literally this sequence as one copy-paste block.

**Build Cost:** Honest estimates for a 2-person team (engineer-weeks of focused work; existing Rust server, HMAC scopes, push lane, quarantine, Debezium endpoint, MCP server, and Python SDK skeleton all reused):

— Generic minted webhook URLs: 1–1.5 weeks for mint/route/HMAC-verify/policy-binding on the raw JSON path. +1 week SPIKE on Rust JSONata maturity before committing to declarative mapping (fallback: constrained subset — paths, object construction, whitelisted functions — or reference JS impl in a WASM sandbox with hard time/depth/output limits; JSONata permits recursion so limits are mandatory either way).
— `verity` CLI: 2–3 weeks. `dev` mode is packaging the existing server + local embedder; `add` leans on `unstructured`; `mcp install`, `webhook mint`, `tail`, `query` are thin API clients. Polish (the refusal messages, the printed next steps) is where the wow lives — budget real time for it.
— Files endpoint (multipart + unstructured in the Python ingest plane): ~1 week.
— Framework sinks: ~1 week each for LlamaIndex and LangChain (the Zep/Mem0 precedent says one class per ecosystem).
— pg_net trigger snippet + docs page: 1–2 days (Debezium lane already built).
— Manifest format + acl_policy + fixtures + `verity manifest test` + admin approval gate: 2.5–3 weeks. The conformance harness ships WITH the format, not after.
— Credential-lifecycle abstraction (static/PAT/client_credentials/refresh-rotation + expiry telemetry): 1–1.5 weeks, built once in the SDK, forced now by Zendesk/Atlassian/Dropbox.
— WebSocket receive lane (generic Socket-Mode-style): 1.5–2 weeks; can ship after GA of the above.
— MCP-spec auth for Verity's own server (RFC 9728 + CIMD): ~1 week.

Total: roughly 12–15 engineer-weeks. Realistic wall clock for two people including docs, packaging, and the inevitable 20% overrun: 8–10 weeks to everything above, but the founder-question answer (MCP writes + webhook mint + CLI) ships in 3–4 weeks. Deferred deliberately: PyAirbyte bridge (1–2 weeks, backfill convenience), OAuth concierge relay (cloud-edition, later), community manifest registry (a repo of YAML files at first — near-zero cost).

**Tradeoffs:** What this lens honestly gives up, and the mitigations:

1. No backfill out of the box. Push gives you "from now on," not history. Mitigations: `verity add` for files, the manifest's optional poll block for API backfill, PyAirbyte bridge later — but a developer wanting "sync my last 5 years of Drive" needs the truth-lane connector, not the Loading Dock. Docs must say so plainly.

2. Lost-webhook gaps. Push without a reconciliation backstop silently drops deliveries (the reason webhook gateways exist). Deterministic PKs + bi-temporal facts absorb duplicates idempotently, but gaps require the manifest poll lane — so "zero source-side code" is aspirational for sources that matter; the poll backstop is quietly a mini-connector.

3. ACL fidelity is policy-based for the long tail. Pushed payloads don't carry per-object ACLs; the Dock leans on admin visibility policies. Full fidelity (Drive permissions.list, Graph /permissions, Salesforce *Share tables) requires source-side pulling — which is why the flagship native connectors stay in scope and why "convenience lane vs truth lane" must never be blurred in docs. The corollary risk: a wrong visibility policy is a permission leak into shared agent memory, the design's highest-severity failure mode; mitigated structurally (fail-closed choke point, mint-time policy binding, narrow-only payloads, human-gated acl_policy, fixtures), never fully eliminated.

4. Webhook receivability drags in networking. A firewalled self-hosted Verity can't receive SaaS webhooks; the WebSocket lane covers Slack-style sources, but Google/Microsoft push needs a public verified HTTPS endpoint — meaning either user-managed exposure or a thin Verity-hosted relay, the same "a small hosted service creeps in anyway" lesson as the OAuth redirect problem. We should embrace one thin relay deliberately (Tailscale model: relay stores nothing) rather than pretend pure OSS avoids it.

5. Burden shifts to the developer for mapping and webhook setup. No per-source connectors means the dev pastes URLs into vendor UIs (HubSpot/Intercom webhook config is UI-only) and writes/approves mappings. Mitigated by the native-envelope convention (zero mapping for well-behaved sources), LLM-drafted manifests with deterministic fixtures, and `verity connect <source>` helpers — but it will never feel as turnkey as Merge's hosted grid, which is precisely the cloud edition's remaining value.

6. Short-lived-token drift erodes "just paste a key." Zendesk kills API tokens by Apr 2027; Atlassian and Dropbox already rotated. The credential-lifecycle abstraction absorbs this, but it means the OSS core carries token-minting plumbing we'd rather not own, and it will grow.

7. Two-edition divergence is real. Merge/concierge/marketplace apps are cloud-only, so OSS and cloud onboarding differ meaningfully; that's a support and messaging cost we accept in exchange for an Apache-2.0 core with zero hosted dependencies and a defensible moat (the ACL/visibility registry + bi-temporal state) that no surveyed competitor carries.

## Verity Sourcefiles — the manifest-first ingestion plane ("connectors are config") (manifest)

**Thesis:** Every REST/webhook source becomes a reviewable YAML manifest — a BYOT auth reference, JSONata field mappings, Airbyte-style cursors/pagination, and a mandatory enum-constrained acl_policy block — executed by the existing Rust ingest runtime, so the connector catalog is data, not code: LLM-draftable from API docs, deterministically conformance-tested against embedded fixtures, human-approved only at the ACL block, and community-hostable in a registry with zero supply-chain code execution. Because 20/20 surveyed systems allow customer-self-provisioned credentials, targeting BYOT eliminates the entire hosted-OAuth burden from the Apache-2.0 core (Merge stays cloud-only, Nango stays optional); what Verity builds instead is the one thing nobody else has — permissions carried in the manifest itself, fail-closed — turning the ACL invariant from a runtime constraint into the product's differentiator and its onboarding grammar.

**Entry Points:** Ranked by funnel order (first touch to deep integration), each reusing the same push lane, quarantine, and scope-handle machinery:

1. `verity dev` + `verity add` (CLI) — embedded local server, local embeddings, one credential total (a Verity scope handle, auto-minted). `verity add ./docs | file.pdf | https://url --crawl | -` with REQUIRED `--visibility <policy>` enforced by the argument parser. This is the first 5 minutes.

2. Minted scoped webhook URLs (generalized POST /v1/ingest/webhook) — `verity source create --type webhook --visibility team:eng` mints a unique signed URL à la Estuary HTTP Ingest; accepts any JSON; a documented Verity-native payload shape (Debezium-outbox-style convention) needs ZERO mapping; unknown shapes land in quarantine-preview where the UI/CLI offers to draft a manifest from captured samples. Ships with a copy-paste Supabase/pg_net trigger snippet as the CDC-lite on-ramp to the Debezium truth lane.

3. MCP write tools on the existing server — ingest_text/remember, ingest_file, ingest_url; scope-handle-gated, required visibility parameter. 'Paste this MCP config into Claude, tell it to save your docs' makes the agent itself the universal connector.

4. Certified manifest registry + credential wizards — `verity connect linear` fetches a signed community manifest, runs the BYOT wizard (create PAT/private app/manifest-app/service account in YOUR tenant, paste it), validates ACL mappability, activates after admin approves the acl_policy. Manifests are data: diffable, reviewable, no supply-chain code execution.

5. LLM-authored manifests for the long tail — `verity manifest new --docs https://api.vendor.com/docs` via the connector-authoring MCP: LLM drafts auth/pagination/streams/mapping (Airbyte AI Assistant + Superglue playbook), auto-generates fixtures, `verity manifest test` gives deterministic pass/fail, human approves ONLY the acl_policy block, activate. Webhook lane for freshness + poll lane from the same manifest as reconciliation backstop.

6. Framework sinks — VerityVectorStore (LlamaIndex) + LangChain vector-store/retriever packages with required visibility_policy constructor args: the proven Zep/Mem0 move that turns 300+ LlamaHub readers and 100-200+ LangChain loaders into free connectors.

7. PyAirbyte destination bridge — `get_source('source-hubspot', config) -> VerityCache`: inherits Airbyte's whole catalog with user-supplied creds, routed through the required-visibility gate.

8. POST /v1/files — multipart drop-a-file; server-side parse/chunk/embed via the Apache-2.0 `unstructured` library.

Native flagship connectors (HubSpot, Drive, Salesforce, Slack, Debezium) remain the truth lane above all of this — the manifest plane is the long tail, not a replacement for source-fidelity ACL connectors.

**Auth Story:** BYOT (bring-your-own-token) is the ONLY auth mode of the Apache-2.0 core, and the research shows this loses nothing: 20/20 surveyed systems let a customer self-provision a first-party credential (PAT, API key, private app, service account, or self-registered OAuth client in their own tenant) with zero vendor-hosted OAuth app, and ~18/20 deliver webhooks under that credential.

Mechanics: the manifest never contains credentials — its `auth:` block is a typed reference to a secret in Verity's secret store, declaring one of four credential SHAPES the Rust runtime knows how to operate: (1) static key/PAT (GitHub fine-grained PAT, Linear, Asana, Airtable, Monday, Front, Gong, Stripe, Notion, HubSpot private-app token, Slack bot token); (2) client_credentials minting (Zendesk's mandated 2026-27 replacement for API tokens, Salesforce connected apps, Box CCG, Microsoft Entra app-only); (3) refresh-token rotation (Dropbox short-lived tokens); (4) service-account JWT (Google DWD). This credential-lifecycle abstraction is built ONCE in the SDK/runtime — with expiry telemetry, token-health checks, and re-establishment hooks for webhooks that die with their token (Asana) — because the industry trend Zendesk leads means 'API key' increasingly means 'self-registered OAuth client with machine grants'.

Onboarding friction is attacked with credential wizards, not OAuth clients: `verity connect slack` opens the browser to api.slack.com/apps preloaded with Verity's shipped app manifest JSON (2-3 min, Socket Mode = push with no public endpoint); `verity connect hubspot` ships the exact private-app scope list and reminds the user of the one manual webhook-subscription UI step; `verity connect gdrive` prints the DWD scope string and deep-links the Admin console (DWD is also the only credential shape that gives whole-domain ACL-faithful Drive ingest, so it's required for the truth lane anyway); everything else is 'create a PAT, paste it'. The wizard validates the pasted credential AND confirms ACL mappability before ingest starts.

Escalation lanes, all optional: developers who want real OAuth flows for their OWN registered apps get a docker-compose profile bundling Nango self-hosted (ELv2 free tier covers exactly flows + refresh + proxy; Verity's connectors keep owning webhooks and ACL fetching; ELv2 internal-use posture needs one legal review, and Verity Cloud must not resell Nango itself). A later free Verity-hosted 'OAuth concierge' (verified shared Slack unlisted-distribution app, CASA'd Google app, marketplace-listed HubSpot app + callback relay that hands refresh tokens DOWN to the self-hosted instance and stores nothing) is cloud-adjacent convenience, never a dependency. Merge stays strictly cloud-edition long tail. For Verity's own MCP surface, implement the 2025-11-25 spec (RFC 9728 Protected Resource Metadata + CIMD URL-as-client_id, DCR fallback) so any MCP client connects to a self-hosted Verity with zero pre-registration — the agent-side mirror of the same no-app-registration principle.

**Acl Story:** The manifest's `acl_policy` block is the load-bearing invariant, and it is designed so it CANNOT be defaulted, inferred, or LLM-authored into existence.

SCHEMA: `acl_policy` is required-by-absence-behavior with exactly three enum-constrained modes. (1) `map` — JSONata/path expressions extract principals from the source payload or a companion permissions fetch (e.g. Drive permissions.list, Graph /permissions, Box collaborations, GitHub collaborators, Salesforce *Share rows), plus a mandatory `identity_namespace` declaration (email | source-native-id | verity-group), copying Glean's isUserReferencedByEmail distinction — the only prior art that carries permissions with pushed content. (2) `static` — a reference (never inline) to an admin-defined visibility policy in Verity's policy registry (e.g. `policy://revenue-org`). (3) `quarantine` — the default when the block is absent, when a `map` expression fails at runtime, or when drift detection sees unexpected-field/mapping-failure rates spike. Fail closed is the runtime posture everywhere: a record that cannot produce a valid AclEnvelope never becomes a queryable fact.

TIERING AS SDK CONTRACT (from the PAT-COVERAGE tiers): Tier A sources (Drive, SharePoint/Graph, Box, Dropbox, GitHub, Jira/Confluence, Salesforce) MUST ship `map` — the certified registry rejects Tier A manifests with `static`. Tier B (Slack channels, Front inboxes, Linear/Asana/Monday teams, Zendesk groups) use `map` against container membership and must set `approximation: true` with a human-readable note that surfaces in the admin approval UI ("channel membership approximates visibility; DMs excluded"). Tier C (Notion, Gong, Intercom, HubSpot CRM records, Stripe, raw DB rows) MUST use `static`, and the connector REFUSES TO START without an assigned policy — the invariant becomes an onboarding step, not a runtime surprise. Postgres/Debezium sources may alternatively declare schema-encoded principal columns in a `map` block (the declarative ACL-mapping config the DB lane always needed).

HUMAN GATE: activating any manifest whose acl_policy is `map` or `static` requires an explicit admin approval action recorded in the audit log; the LLM authoring flow emits manifests with the acl_policy block literally absent (schema has no default value to hallucinate), so an unreviewed LLM manifest can only ever quarantine. Fixtures embedded in the manifest assert expected AclEnvelopes, so `verity manifest test` verifies ACL extraction deterministically before a byte of real data flows. This is the one failure class unique to Verity — a wrong mapping is a permission leak into shared agent memory, not a broken sync — so it gets structural, not documentary, protection.

CONVENIENCE-LANE FALLBACK: every un-ACL'd entry point (CLI `verity add`, minted webhook URLs, MCP write tools, LlamaIndex/LangChain sinks, PyAirbyte bridge, /v1/files) requires an explicit visibility policy at the argument-parser / constructor / URL-mint level — omitting `--visibility` is a usage error, not a quarantine event. Docs consistently present two lanes: convenience lane = admin-assigned visibility, truth lane = native connectors + Debezium + Tier A manifests with source-fidelity ACLs. Bi-temporal facts retain ACL provenance (which manifest version, which mapping expression, which approval) so a bad mapping is auditable and revocable retroactively.

**Tradeoffs:** 1) The ~80% ceiling: Airbyte's own ecosystem shows declarative manifests cover roughly 4 of 5 REST sources; the weird 20% (session-token dances, GraphQL cursors, binary payloads, Salesforce sharing recalculation) still needs the Python SDK escape hatch. Accepted: the manifest plane is the long tail, natives are the truth lane — but this means maintaining two connector idioms forever.

2) JSONata-in-Rust is the biggest technical unknown (flagged as unverified inference in the research). If crates are immature, the choices are a WASM-sandboxed reference implementation (perf + complexity cost) or a Verity subset (LLM drafts may emit unsupported functions, hurting the authoring loop). The manifest declares its mapping dialect so the subset can grow, but early manifests may be rewritten.

3) Webhook receivability is genuinely unsolved for laptops/firewalled self-hosters: Google/Microsoft push requires a public verified HTTPS endpoint. Mitigations — Socket-Mode-style WebSocket lane (generic, Slack-first), the poll/reconciliation lane as universal fallback, and eventually a cloud relay — but 'push > poll' degrades to poll for some self-hosted topologies, honestly.

4) Deliberate friction on ACLs: the admin-approval gate and refuse-to-start-without-policy behavior for Tier C sources make Verity's funnel one step longer than Chroma-style tools. This is the invariant made visible; some fraction of evaluators will bounce at that step. The bet is that the buyers who matter (enterprise agent teams) convert BECAUSE of it. Similarly, Tier B 'approximation: true' ACLs and Tier C static policies are honest but weaker than the marketing phrase 'ACLs ride with content' — docs must keep the two-lane distinction loud or trust erodes.

5) LLM-authored manifests inherit Airbyte's documented failure modes (inconsistent docs, JS-rendered doc sites, hallucinated pagination); the fixture harness catches mapping errors but cannot catch a semantically-wrong-but-schema-valid mapping — human review of drafted manifests remains real work, and registry moderation is an unbudgeted ongoing tax.

6) Credential-lifecycle plumbing (client_credentials minting, refresh rotation, expiry telemetry) is unavoidable now — Zendesk kills API tokens by Apr 2027, Atlassian scoped tokens are live, Dropbox is short-lived-only — so the 'BYOT is simple' story quietly requires 2-3 weeks of token machinery, and more vendors will follow Zendesk.

7) Strategic: making connectors config lowers Verity's own moat on connector breadth (anyone can fork the registry). The durable value must live where the research says it does — the bi-temporal fact store, per-source cursor state, ACL/visibility policy registry, and lineage — not in the manifests themselves. Two items need re-verification before GA docs: HubSpot Service Keys webhook support and Gong rate limits.

## Verity Sink-First Ingestion Plane ("Be the best sink, never the loader") (ecosystem)

**Thesis:** Extraction is commoditized; permission-aware destinations are not. In 2026 the world already has 300+ LlamaHub readers, 100-200+ LangChain loaders, PyAirbyte's on-demand connector catalog (~80% pure-YAML manifests), Debezium CDC, and — the newest and fastest-growing extractor of all — coding agents wielding MCP tools. Verity should build ZERO loaders and zero OAuth clients, and instead ship six thin sink adapters that make every existing extractor a de-facto Verity connector, with the ACL invariant enforced structurally (required visibility_policy arguments, enum-constrained acl_policy manifest blocks, fail-closed quarantine) rather than by documentation. Docs present two honest lanes: the CONVENIENCE LANE (sinks/CLI/MCP/webhooks — admin-assigned visibility, snapshot-grade) as the adoption wedge, and the TRUTH LANE (native flagship connectors + Debezium — source-fidelity AclEnvelopes, bi-temporal, 31ms-to-queryable) as the graduation path. Durable value concentrates in what only Verity owns: the bi-temporal fact store, per-source cursors, and the visibility-policy/ACL registry — the entry points are deliberately cheap, numerous, and disposable. This answers the founder directly: a developer with no Merge account plugs in any source using credentials THEY already hold (BYOT works for 20/20 surveyed systems), through an extractor someone else already maintains, into a sink Verity wrote once.

**Entry Points:** Ranked by funnel order (first touch → deepest commitment), each reusing the existing push lane, scope handles, and quarantine machinery: (1) MCP WRITE TOOLS on the existing MCP server — ingest_text/remember, ingest_file, ingest_url, each with a REQUIRED visibility parameter and scope-handle-gated writes. The agent itself is the universal connector: 'paste this MCP config into Claude Code, tell it to save your docs.' This is the first touch because it requires installing nothing new for users already in Claude/Cursor. (2) `verity` CLI with `verity dev` (embedded local server + bundled local embeddings, Chroma/Turbopuffer pattern — zero third-party keys) and one verb: `verity add file.pdf | ./dir | https://url --crawl | -` with --visibility REQUIRED by the argument parser. (3) GENERIC SCOPED WEBHOOK URLS (Estuary HTTP Ingest pattern): `verity source create --type webhook` mints a unique signed URL per source; accepts any JSON; optional 15-line YAML manifest with JSONata field mapping, predicate event routing, and a mandatory acl_policy block {map|static|quarantine}; unmapped or absent → HTTP-accepted-but-quarantined. Ship the copy-paste Supabase/Postgres pg_net trigger snippet as CDC-lite on-ramp to the existing Debezium lane, and a documented 'Verity-native webhook shape' that needs zero mapping (Debezium-outbox convention style). (4) FRAMEWORK SINKS: VerityVectorStore for LlamaIndex and a LangChain vector-store/retriever package — the proven Zep/Mem0 move that converts every loader in both ecosystems into a free Verity connector; visibility_policy is a required constructor argument, no default. (5) PYAIRBYTE VERITY DESTINATION/CACHE class: `get_source('source-hubspot', config=my_creds).read(cache=verity_cache)` inherits Airbyte's entire catalog with user-supplied credentials; same required-visibility gate; preserve Airbyte stream/state metadata as Verity source cursors. (6) MULTIPART POST /v1/files — drop-a-file, server-side parse→chunk→embed via the Apache-2.0 `unstructured` library (license-compatible), mirroring the OpenAI/Anthropic pattern. (7) GRADUATION: native flagship connectors (HubSpot, Drive, Salesforce, Slack, Debezium) + community manifest registry (manifests are data — reviewable YAML, no supply-chain code execution) for teams that outgrow snapshots and need source-fidelity ACLs + push freshness. Explicitly NOT built: per-source loaders, per-source OAuth clients, a no-code connector-builder UI (the connector-authoring MCP + manifest format lets coding agents draft manifests Airbyte-AI-Assistant-style, with the acl_policy block excluded from LLM defaults and human-approval-gated), and document parsers.

**Auth Story:** Two halves, neither requiring Verity to host an OAuth app. AUTH TO VERITY: exactly one credential — the existing HMAC scope handle — for CLI, webhooks, sinks, and PyAirbyte; for the MCP surface, implement the 2025-11-25 MCP spec (RFC 9728 Protected Resource Metadata + CIMD URL-as-client_id, DCR fallback) so any MCP client connects to a self-hosted Verity with zero pre-registration. AUTH TO SOURCES: pushed entirely onto the extractor ecosystems and BYOT, which the coverage survey shows works for 20/20 systems — LlamaHub/LangChain loaders and PyAirbyte sources take the user's own PAT/API key/private-app token/service-account JSON in their config; webhook sources use the source system's own signing secret (HMAC verification declared in the manifest); Postgres uses DB credentials via the existing Debezium lane. Verity never sees a vendor OAuth dance in the OSS core. For the truth-lane flagship connectors, ship zero-OAuth credential wizards (`verity connect slack` → app-from-manifest JSON, ~3 min; HubSpot private-app scope list, ~2 min; Google service-account + domain-wide delegation — also the only credential shape that supports whole-domain ACL-faithful Drive ingest) plus one shared credential-lifecycle abstraction in the SDK — {static key | PAT | client_credentials minting | refresh-token rotation} with expiry telemetry — because Zendesk (tokens dead Apr 2027), Atlassian (scoped tokens + api.atlassian.com), and Dropbox (short-lived tokens) already require it and the industry is drifting from static keys to customer-created OAuth clients with machine grants. Nango self-hosted (ELv2, auth+proxy free tier) stays a strictly optional docker-compose profile for developers who register their own OAuth apps (pending ELv2 legal review); Merge and any hosted OAuth concierge remain cloud-edition-only. Documented fact vs inference note: BYOT coverage and vendor mechanisms are documented; the '<10-minute connect' timings and ELv2 internal-use posture are inference/pending-counsel.

**Acl Story:** Honest accounting per entry point, because every convenience-lane extractor strips source ACLs by construction — so the invariant is enforced by types and parsers, not docs. (1) MCP tools: visibility is a required tool parameter; the scope handle bounds the maximum visibility the caller may assign (an agent with a team-scoped handle cannot write org-visible facts); omitted → tool error, never silent default. (2) CLI: --visibility is a required argument; `verity add` refuses to run without it; local files carry no principal metadata so this IS the explicit admin-assigned-visibility fallback. (3) Webhook manifests: mandatory enum-constrained acl_policy block with three modes matching the existing invariant — `map` (JSONata expressions extracting principals from the payload, with declared identity namespace à la Glean's isUserReferencedByEmail vs native-id), `static` (reference to a registered visibility policy), `quarantine` (the behavior when the block is absent or mapping fails at runtime). Manifests with map/static require an explicit admin approval step before activation, and the LLM connector-authoring flow is structurally forbidden from emitting the acl_policy block — this is the highest-severity failure mode in the whole design (a wrong acl_policy is not a broken sync, it is a permission leak into shared agent memory) and no prior art exists to borrow from. (4) Framework sinks and (5) PyAirbyte destination: required visibility_policy constructor argument (no kwarg default); anything arriving without one lands in the existing fail-closed quarantine, making bypass impossible rather than discouraged. (6) Files endpoint: visibility_policy required in the multipart request. (7) Truth lane: native connectors emit real AclEnvelopes per the SDK contract tiers — Tier A sources (Drive, SharePoint, Box, Dropbox, GitHub, Jira/Confluence, Salesforce) MUST mirror per-object ACLs; Tier B (Slack channels, Front inboxes, Linear teams…) emit container-membership ACLs with a documented approximation note; Tier C connectors (Notion, Gong, Intercom, HubSpot CRM, Stripe, raw DBs) refuse to start without an admin-assigned visibility policy, turning quarantine into an onboarding step instead of a runtime surprise. Every fact records ACL provenance (mirrored | approximated | admin-assigned | quarantined) so query-time consumers and auditors can distinguish fidelity classes — this provenance dimension is the moat no surveyed competitor carries.

**Five Minute Wow:** Minute 0: `pipx install verity` (or brew). Minute 1: `verity dev` — boots the embedded Rust server with bundled local embeddings (no Docker, no Postgres, no third-party API key), prints a dev scope handle, a ready-to-paste MCP config block, and a minted webhook URL. Minute 2: paste the MCP config into Claude Code / Claude Desktop (or run the printed one-liner `claude mcp add verity ...`). Minute 3: either tell the agent 'save everything in ./docs to Verity, visible to the eng team' — the agent calls ingest_file with visibility=eng and the scope handle authorizes it — or run `verity add ./docs --visibility eng` directly (forgetting --visibility produces an argument-parser error that names the invariant, the first teaching moment). Minute 4: ask the agent a question; it calls verity_search and answers from ingested facts, and the response shows the visibility label and ACL-provenance tag on each hit. Minute 5: `curl -X POST <minted-webhook-url> -d '{"event":"deal.updated",...}'` and watch the fact become queryable in ~31ms — then the CLI prints the graduation hint: 'want source-fidelity ACLs and live sync? verity connect slack'. One credential total (the scope handle Verity itself minted), zero vendor consoles, zero OAuth, no Merge account, and the permission invariant was demonstrated — not just documented — inside the first five minutes.

**Build Cost:** Honest estimates for a 2-person team (assumes existing REST API, scope handles, quarantine, MCP server, local embeddings, Debezium lane): (1) MCP write tools: 3-5 days — server exists; work is tool schemas, visibility-vs-scope-handle enforcement, tests. (2) verity CLI + `verity dev` embedded mode: 1.5-2.5 weeks — the CLI verbs are days, the embedded single-binary dev server (SQLite-or-embedded storage + bundled embedder) is the real work and is the highest-leverage single item. (3) Generic webhook URLs + manifest v0: 2-3 weeks, INCLUDING a mandatory 1-week spike on Rust JSONata evaluator maturity (jsonata-rs lineage is unverified — fallback is a constrained path+whitelisted-function subset or the reference JS impl in a WASM sandbox with hard eval limits: time, depth, output size, no network). Predicate routing + acl_policy enum + admin approval gate ride on this. (4) LlamaIndex VerityVectorStore: ~1 week. (5) LangChain package: ~1 week (much shared code with #4). (6) PyAirbyte destination/cache: 1.5-2 weeks — the interface is documented but stream-state-to-cursor mapping and the visibility gate need care. (7) Files endpoint with embedded `unstructured`: ~1 week riding on the Python ingest plane. (8) Conformance harness (`verity manifest test` + fixtures[] in manifests) — ship WITH the manifest format, not after: ~1 week. (9) Connector-authoring MCP (LLM drafts manifests, acl_policy excluded): ~1 week, deferred to after the harness exists. Total: roughly 10-13 engineering-weeks ≈ one quarter for two people including docs, with a clean sequencing: MCP tools + CLI first (the wow), webhooks + harness second (the long tail), sinks + PyAirbyte third (the multiplier), files + authoring MCP last. Ongoing tax to budget honestly: framework-version churn on the two sink packages (~2-4 days/quarter), PyAirbyte interface drift, and JSONata sandbox maintenance.

**Tradeoffs:** (1) Convenience-lane data is snapshot-grade: loaders and PyAirbyte give no push freshness, no per-object ACLs, and weaker lineage than the truth lane — mitigated by explicit ACL-provenance tagging and in-product graduation prompts, but a customer who never graduates has coarser permissions than the marketing implies; docs must never blur the two lanes. (2) Coarse visibility policies fail in both directions: over-broad policy leaks, over-narrow policy hides — the required-argument design prevents SILENT failure but cannot prevent a wrong admin choice; audit views (what policy covers which source) are the compensating control and are in-scope for the registry. (3) Dependency on ecosystems Verity doesn't control: LlamaIndex/LangChain APIs churn, PyAirbyte could change its cache/destination interface, and loader quality is uneven — accepted deliberately because entry points are disposable by design and durable state lives in Verity. (4) Not hosting OAuth means no one-click connect in the OSS core; enterprise buyers who demand it are intentionally routed to the cloud edition (Merge long-tail, future OAuth concierge) — this is the open-core line, drawn on convenience rather than capability. (5) JSONata-in-Rust is the one unresolved technical risk (labeled inference, needs the spike); the WASM-sandbox fallback adds latency and operational surface to an otherwise clean Rust server. (6) The LLM-authored-manifest path imports Airbyte's documented failure modes (hallucinated pagination, doc drift) plus Verity's unique one — a wrong acl_policy is a permission leak, not a broken sync — which is why acl_policy is human-gated and LLM-excluded even though that adds onboarding friction. (7) Fast-moving external facts to re-verify before GA docs: HubSpot Service Keys webhook support, Zendesk migration tooling, Gong rate limits against a real contract, and the Nango ELv2 internal-use legal posture. (8) Opportunity cost: a quarter spent on sinks is a quarter not spent on more Tier A native connectors — justified because sinks multiply coverage by hundreds of sources per engineering-week while each native connector adds exactly one, and because the truth lane already has its flagship five.

## Judge

**Layered recommendation:** The three proposals share roughly 70% of their bill of materials (MCP write tools, verity dev + CLI, minted webhook URLs, quarantine choke point, acl_policy manifests, framework sinks, files endpoint via unstructured, BYOT credential wizards, credential-lifecycle abstraction, optional Nango profile, MCP 2025-11-25 auth). They differ almost entirely in SEQUENCING and center of gravity — which confirms they are layers, not rivals. The right funnel takes P1's spine, P2's climax and ACL schema, and P3's multiplier and provenance taxonomy:

LAYER 0 — Weeks 1-4, the direct founder answer (P1's sequencing, items 1-4): MCP write tools on the existing server (2-4 days), the verity CLI with `verity dev` embedded server + local embeddings + required --visibility, canonical envelope endpoints, and minted scoped webhook URLs with STATIC visibility binding only — accept the documented Verity-native payload shape with zero mapping, land unknown shapes in quarantine-preview, and defer all declarative mapping to Layer 2. This ships the 5-minute wow in under a month with one credential (the HMAC scope handle) and zero OAuth anywhere. One critical substitution: steal P2's demo climax as minute 4-5 — `verity handle create --as intern@co`, re-run the same query, watch team-scoped facts disappear. P1 demos ingestion speed; P2's moment demos the moat. Ingestion speed is table stakes in 2026; permission-differentiated memory is the thing no surveyed competitor does. Also adopt P3's ACL-provenance tag (mirrored | approximated | admin-assigned | quarantined) on every fact from day one — it is cheap now, retrofit-expensive later, and it is what keeps the two-lane story honest in the product rather than in docs.

LAYER 1 — Weeks 4-8, the multiplier (P3's items 4 and 6, P1's items 5-7): files endpoint riding unstructured (~1 wk), LlamaIndex VerityVectorStore + LangChain package (~2 wks, required visibility_policy constructor args) — hundreds of sources for two weeks of work, positioned explicitly in docs as the snapshot-grade convenience lane. The pg_net/Supabase trigger snippet (1-2 days, the Debezium lane already exists). Start the credential-lifecycle abstraction (static | PAT | client_credentials | refresh-rotation, ~1.5-2 wks) — all three proposals independently conclude Zendesk/Atlassian/Dropbox force it now; treat that unanimity as settled. Two credential wizards only: `verity connect slack` (app-from-manifest, Socket Mode) and `verity connect github` (fine-grained PAT used once from the dev's machine to register a webhook at a minted URL — P1's best pattern, the credential never stored).

LAYER 2 — Weeks 8-12, the scaling substrate (P2's core, descoped): manifest v1 with the acl_policy block exactly as P2 specifies it — enum-constrained {map | static | quarantine}, no defaultable value, identity_namespace declaration, tier contracts (Tier A must map, Tier B approximation:true, Tier C refuse-to-start), admin approval in the audit log, and fixtures[] + `verity manifest test` shipping WITH the format. P2's ACL schema is the best-engineered artifact in any proposal and should be adopted verbatim regardless of which lens wins. Run the JSONata validation (jsonata-core, pure Rust, claims full 2.1.0 conformance — verified via crates.io/lib.rs this week) in week 2-3 OFF the critical path; if it holds, the mapping dialect question closes early. Poll/reconciliation block ships minimal (cursor echo + interval) — it is the honest answer to P1's lost-webhook gap, not a full Airbyte paginator.

CLOUD EDITION unchanged and untouched by any of this: Merge remains the long-tail managed grid, the future OAuth concierge remains cloud-adjacent, and the open-core line is drawn where P3 articulates it best — on convenience, not capability.

Why this composition wins on the five lenses: it takes P1's time-to-wow (the runway constraint is binding), P3's coverage-per-hour (sinks in weeks 4-8, not deferred), P2's ACL integrity and 100-source maintenance story (manifests as the only community-scaling mechanism), and preserves the Merge split all three agree on. Total is ~13-15 engineer-weeks — inside the 12-week wall clock for two people with parallel Rust/Python tracks, with the founder-question answer live at week 4.

**Cut list:** CUT OUTRIGHT from v0.1 (either speculative, duplicative, or thesis-eroding):
1. Generic WebSocket receive lane (P1, 1.5-2 wks) — only Slack actually offers Socket Mode today; building a 'generic' lane for one confirmed consumer is speculation. Slack's native connector uses Socket Mode directly; revisit if a second vendor ships the pattern.
2. PyAirbyte destination bridge (P2 item 7, P3 item 5; 1.5-2 wks) — batch-only, interface-drift-prone, redundant with the framework sinks for snapshot ingestion, and the lane most likely to blur the convenience/truth distinction. P1's instinct to defer it is right.
3. LLM manifest-authoring MCP (2-3 wks + 'ongoing tuning forever') — sequencing error to build before the manifest format and conformance harness have survived contact with real community authors. Quarter 2 at the earliest.
4. Community manifest registry infrastructure — a git repo of signed YAML files costs near zero and is sufficient for v0.1; certification tiers, moderation, and `verity connect <name>` fetch machinery wait until there are ≥10 community manifests to certify. The moderation tax all proposals flag as unbudgeted stays unincurred.
5. Verity-hosted webhook relay for Google/Microsoft push (P1 tradeoff 4's 'embrace one thin relay') — correct long-term instinct, wrong quarter; it is a hosted service with an SLA. Document the delta-poll fallback (Drive changes.list, Graph delta) as the self-hosted answer and put the relay in the cloud edition.
6. Quarantine-preview 'draft a manifest from captured samples' UI (P2 item 2) — quarantine + `verity tail` showing raw payloads is 90% of the value; the drafting UI is polish.

CONFIRMED CUTS (unanimous across all three proposals — treat as settled and stop re-litigating): per-source OAuth clients in the OSS core (zero, ever); no-code connector-builder UI; writing our own document parsers (embed unstructured); Keycloak or any identity-server dependency; Composio/Arcade dependencies; Merge in the OSS core.
