## Competitive Landscape (mid-2026)

The agent-memory category has matured dramatically by mid-2026 but has also fragmented into distinct sub-categories: conversational/personalization memory (Mem0, Memobase, Honcho), temporal knowledge-graph memory (Zep/Graphiti, Cognee), agent-managed context (Letta, with its 2026 pivot to git-backed MemFS "context repositories"), research-grade memory OSes (MemOS/MemTensor), and closed enterprise context platforms (Supermemory, Graphlit, Glean, Salesforce's internal agentic memory). The dominant technical convergence is HYBRID retrieval — vector + BM25 + graph traversal over a (bi-)temporal knowledge graph — with the pure-vector-DB approach now widely considered insufficient for temporal reasoning and multi-hop queries. Benchmarks standardized around LoCoMo, LongMemEval, and BEAM; token efficiency and latency are now reported alongside accuracy. On latency, the best published numbers are Zep's sub-200ms p95 retrieval flat from 10K to 100M-node graphs and Letta's ~300ms p95; Mem0 reports 0.88s p50. Nobody publicly claims low-tens-of-milliseconds retrieval, so our 10-30ms target would be genuinely differentiating — achievable only with a server-side hot path with precomputed scope filters, decoupled from the slow async write/consolidation path (which every serious system already does asynchronously).

The licensing pattern is nearly uniform: Apache-2.0 open core (Mem0 60.5k stars, Graphiti 28.6k, Cognee 27.4k, Letta 23.7k, Memobase) plus a closed managed cloud; Honcho is the AGPL outlier and Supermemory is fully closed. Zep is the cautionary tale — it discontinued its open-source Community Edition (April 2025, further retirements Feb 2026) because maintaining a forked OSS server alongside the commercial multi-tenant service was untenable; its OSS investment retreated to the Graphiti engine only. Funding is real but early: Mem0 $24M Series A (Oct 2025), Letta $10M seed at $70M post, Cognee $7.5M seed, Supermemory seed-stage — no one has won the category.

The gaps map almost exactly onto this project's hard requirements. (1) Permission-scoped recall: essentially NO open-source memory framework does source-ACL-inherited, principal-aware retrieval; Cognee has tenant isolation and MemOS has permission control "in the design," but real permission-aware retrieval today lives only in proprietary enterprise search (Glean, Onyx, Azure AI Search security filters), and the 2026 practitioner literature explicitly identifies ACL sync from SharePoint/Drive/Salesforce into the retrieval layer as an unsolved, roll-your-own problem. (2) Live sync from systems of record: only closed platforms (Supermemory connectors with webhook live-sync, Graphlit continuous ingestion, Glean Live Mode) do this; all OSS frameworks assume the application pushes memories in. (3) Cross-framework shared memory: MCP is now supported by every major framework and is the only credible cross-framework interface, but existing MCP memory servers (OpenMemory) are local-first, single-user developer tools, not multi-tenant enterprise services. (4) Multimodal ingestion is thin everywhere except Graphlit (proprietary). Mem0's own "State of AI Agent Memory 2026" report concedes that privacy/consent/deletion architecture and memory staleness remain "genuinely unsolved" and are punted to the application layer. An open-source system combining permission-inherited scoped recall + CDC/webhook connector framework + MCP-first multi-agent shared memory + sub-50ms retrieval would occupy space nobody currently holds.

### Key findings
- **Mem0 is the traction leader: 60.5k GitHub stars, Apache-2.0, $24M Series A (Oct 2025, Basis Set Ventures), ~14M downloads, 21 framework integrations. Architecture is hybrid vector + knowledge graph + key-value with three-tier scoping (user/session/agent). April 2026 algorithm update added single-pass extraction, entity linking, and temporal reasoning (LoCoMo 92.5, ~0.88s p50). Its README/docs contain no permission model, no enterprise-source sync, and no true multi-agent shared memory — scoping is by user_id, not by principals/ACLs.** — _https://github.com/mem0ai/mem0 (fetched 2026-07-09); https://mem0.ai/blog/state-of-ai-agent-memory-2026_
  - Implication: The category leader validates demand but competes on personalization memory, not enterprise shared context. We should not out-Mem0 Mem0 on chat memory; we should own the permission-aware enterprise context layer it explicitly leaves to the application.
- **Zep/Graphiti validated the temporal (bi-temporal) knowledge graph as the best freshness model: every fact carries valid-time windows and superseded facts are invalidated rather than deleted, with full provenance back to source 'episodes'. Graphiti: 28.6k stars, Apache-2.0, v0.29.2 (June 2026), Neo4j/FalkorDB/Neptune backends, hybrid semantic+BM25+graph retrieval, MCP server included. Zep cloud claims sub-200ms p95 retrieval flat from 10K to 100M-node graphs — the best published latency in the category.** — _https://github.com/getzep/graphiti (fetched 2026-07-09); https://blog.getzep.com/scaling-agent-memory-zep-30x/; https://arxiv.org/abs/2501.13956_
  - Implication: Adopt the bi-temporal fact model (valid_from/valid_to + provenance) — it directly solves 'live updates' semantics (a new opportunity stage supersedes the old one instead of duplicating). Zep's latency curve proves ~150-200ms p95 is achievable at 100M scale; beating it into low tens of ms requires precomputed scope filters and an in-memory hot path.
- **Zep discontinued its open-source Community Edition (April 2025; final feature retirements Feb 2026), moving code to a legacy folder and concentrating OSS effort on the Graphiti engine only. Stated reason: maintaining a community-supported server fork alongside a multi-tenant commercial service led to chronic under-investment in the OSS version.** — _https://blog.getzep.com/announcing-a-new-direction-for-zeps-open-source-strategy/_
  - Implication: Critical open-core lesson: do NOT ship a separate OSS server and cloud server codebase. The OSS artifact should be the real engine (single codebase), with cloud value in managed connectors, multi-tenancy at fleet scale, SSO/SCIM, and operations — not in withheld core features.
- **Letta (MemGPT): 23.7k stars, Apache-2.0, $10M seed (Felicis, $70M post). Its paradigm is the agent self-managing memory via tool calls; in Feb 2026 it pivoted to 'Context Repositories' — git-backed memory files (MemFS) with client-side sleep-time subagents doing async memory consolidation. p95 ~300ms. It is increasingly an agent framework, not a shared memory service.** — _https://github.com/letta-ai/letta (fetched 2026-07-09); https://www.letta.com/blog/sleep-time-compute/; https://www.letta.com/blog/our-next-phase/_
  - Implication: Two ideas worth stealing: (1) async 'sleep-time' consolidation — expensive memory rewriting happens off the hot path; (2) versioned memory (git-like history) aids auditability. But Letta confirms nobody is building framework-agnostic SHARED memory — its memory is bound to Letta agents.
- **Cognee: 27.4k stars, Apache-2.0, $7.5M seed, v1.2.2 (July 2026). Graph-native ECL (Extract-Cognify-Load) pipeline, defaults to Postgres+pgvector with pluggable graph stores (Kuzu/Neo4j/FalkorDB/Neptune/Memgraph), 14 retrieval modes, and — uniquely among OSS frameworks — advertises agentic user/tenant isolation with audit trails and OpenTelemetry observability.** — _https://github.com/topoteretes/cognee (fetched 2026-07-09); https://www.cognee.ai/blog/cognee-news/cognee-raises-seven-million-five-hundred-thousand-dollars-seed_
  - Implication: Cognee is the closest OSS architecture to our concept (graph+vector, pluggable stores, tenant isolation) and the most direct competitor for 'open-source enterprise memory.' Its gap: no source-system connectors/CDC, no ACL inheritance, tenant-level (not principal-level) isolation. Postgres+pgvector-by-default is a proven adoption-friendly packaging choice.
- **LangMem is alive but stagnant: it survived LangChain 1.0 (which deprecated legacy memory classes) and has ~746K monthly downloads, but its last PyPI release (0.0.30) was Oct 2025 — 8+ months without a release — and it remains LangGraph-native.** — _https://github.com/langchain-ai/langmem; https://db0.ai/blog/langchain-memory-deprecated_
  - Implication: Framework-native memory is losing to framework-agnostic services; LangChain itself under-invests here. Reinforces the framework-agnostic + MCP-first bet.
- **MemOS (MemTensor) is the research-grade 'memory OS': MemCube abstraction unifying plaintext/activation/parameter memory, with scheduling, layering, API abstraction, and notably PERMISSION CONTROL as first-class OS-style governance; Next-Scene Prediction preloads memory to cut latency. Strong benchmarks (LoCoMo 88.8, LongMemEval 89.2, July 2026) but limited Western enterprise adoption.** — _https://github.com/MemTensor/MemOS; https://huggingface.co/papers/2507.03724; https://arxiv.org/pdf/2603.18330_
  - Implication: Validates permission control and memory scheduling as architectural first-class citizens (the academic literature — e.g., MemArchitect on policy-driven memory governance — is converging on this too), but leaves the market position open: nobody has productized governed memory for Western enterprises.
- **Newer entrants specialize rather than generalize: Hindsight (four typed memory networks — world/experience/opinion/entity — LongMemEval 94.6); Honcho (Plastic Labs, AGPL-3.0, background-reasoned 'peer representations', LongMem-S 90.4); Memobase (Apache-2.0, typed user-profile ontology on FastAPI+Postgres+Redis+pgvector); EverMind/EverOS (markdown-file-first memory); Supermemory (closed-source all-in-one context API with connectors).** — _https://www.graphlit.com/blog/survey-of-ai-agent-memory-frameworks; https://arxiv.org/html/2512.12818v1; https://github.com/plastic-labs/honcho; https://github.com/memodb-io/memobase_
  - Implication: The label 'agent memory' now covers 6+ different products. Positioning must be explicit: we are the shared enterprise context/memory layer (organizational knowledge, scoped), not per-user personalization memory. Interop with (not replacement of) Mem0/Letta-style personal memory is a sane stance.
- **GAP 1 — Permission-scoped recall is the biggest hole in OSS. The 2026 practitioner consensus: vector/memory stores 'have no concept of who is asking'; security must move to the retrieval layer with candidate filtering BEFORE the LLM sees context; source ACLs (SharePoint, Drive, Salesforce) change hourly and must be synced via polling/webhooks and normalized into a master principals schema (ReBAC recommended). Only proprietary platforms (Glean, Onyx, Azure AI Search security filters) do permission-aware retrieval today; no OSS agent-memory framework inherits source ACLs.** — _https://tianpan.co/blog/2026-05-04-permission-aware-retrieval-enterprise-rag-access-control; https://truto.one/blog/how-to-maintain-document-level-rbac-in-enterprise-rag-pipelines/; https://www.useparagon.com/learn/permissions-access-control-for-production-rag-apps/_
  - Implication: This is our primary wedge. Build a Zanzibar-style ReBAC principal model (OpenFGA/SpiceDB-compatible) into the core, with connector-level ACL ingestion and pre-filter (not post-filter) enforcement compiled into every retrieval query. This is also the hardest thing to bolt on later — a defensible reason to exist.
- **GAP 2 — Live sync from systems of record exists only in closed products. Supermemory offers connectors (Notion, Drive, Gmail, S3) with initial import + webhook-driven real-time updates ('without live sync, your agent answers with yesterday's information') but is closed-source and was criticized for its proxy architecture adding latency to every LLM call. Graphlit does continuous multimodal ingestion (Slack/GitHub/Jira/Gmail, PDFs/audio/video) — proprietary. Glean's Salesforce connector adds query-time 'Live Mode' for permission-aware freshness. Every OSS memory framework instead assumes the app pushes memories in.** — _https://supermemory.ai/connectors/; https://www.graphlit.com/blog/survey-of-ai-agent-memory-frameworks; https://docs.glean.com/connectors/native/salesforce/about_
  - Implication: An open-source CDC/webhook connector framework (CRM, ticketing, docs, wikis, web) feeding a temporal graph is unclaimed territory. Managed always-on connector fleet + ACL sync is simultaneously the natural cloud monetization line — hosting connectors is genuinely operationally hard, so the open-core split is honest.
- **GAP 3 — Cross-framework shared memory only exists via MCP, and only for individuals. MCP is now supported by LangChain/LangGraph, CrewAI, AutoGen, OpenAI and Anthropic SDKs, making it the de facto cross-framework interface; Graphiti and Mem0 ship MCP servers. But the flagship 'shared across tools' product — OpenMemory MCP — is explicitly local-first, single-developer (Docker+Postgres+Qdrant on your machine). The Graphlit survey names cross-framework sharing and governance as gaps: 'framework-native SharedMemory lacks governance controls; MCP-based delivery works across frameworks and adds the governance layer.'** — _https://mem0.ai/blog/introducing-openmemory-mcp; https://www.graphlit.com/blog/survey-of-ai-agent-memory-frameworks; https://atlan.com/know/context-management-multi-agent-systems/_
  - Implication: Ship an enterprise-grade, multi-tenant MCP memory server as the first-class interface (plus thin native SDKs and a REST/gRPC hot path for sub-50ms use, since MCP adds transport overhead). 'OpenMemory for organizations, with permissions' is an immediately legible positioning.
- **Latency reality check: best published numbers are Zep sub-200ms p95 (148-168ms across 10K→100M nodes), Letta ~300ms p95, Mem0 0.88s p50 / 1.44s p95 (vs 17.1s p95 full-context). Nobody claims low tens of milliseconds. All serious systems already split fast reads from slow async writes (extraction/consolidation off the hot path). Benchmarks standardized on LoCoMo, LongMemEval, BEAM (1M-10M tokens), with token-efficiency (~6.9K vs ~26K tokens/query) as the production differentiator; Mem0's own report lists staleness, privacy/deletion architecture, and cross-session identity as 'genuinely unsolved'.** — _https://blog.getzep.com/scaling-agent-memory-zep-30x/; https://mem0.ai/blog/state-of-ai-agent-memory-2026; https://hydradb.com/blog/mem0-vs-zep-vs-letta_
  - Implication: A 10-30ms retrieval target is credible differentiation but requires: server-side in-memory ANN + inverted index, precompiled scope/permission filters (no runtime ACL resolution), no LLM in the read path, and async ingestion. We must publish latency-vs-scale curves like Zep's, and ideally define a new 'scoped recall / leakage' benchmark — none exists, and defining it would let us define the category.
- **Incumbent pressure is real but siloed: Salesforce runs an internal 'agentic memory' platform over Data 360 connectors for Agentforce; Glean agents use its permission-aware enterprise graph; Notion turned its workspace into an agent hub (May 2026). All are closed, single-vendor ecosystems that lock memory to their platform.** — _https://engineering.salesforce.com/how-agentic-memory-enables-durable-reliable-ai-agents-across-millions-of-enterprise-users/; https://www.glean.com/blog/agent-sandbox-2026; https://techcrunch.com/2026/05/13/notion-just-turned-its-workspace-into-a-hub-for-ai-agents/_
  - Implication: The counter-positioning writes itself: vendor-neutral, open-source, framework-agnostic shared memory that spans ALL systems of record — the Postgres/Kafka play against per-vendor memory silos. Enterprises with agents on 4+ platforms need exactly this neutral layer.

### Recommendations
1) POSITIONING: Do not build another personalization-memory library — that race (Mem0, Memobase, Honcho) is crowded and benchmark-saturated. Build the missing thing: an open-source, permission-aware SHARED CONTEXT layer synced live from systems of record. Think 'open-source Glean-for-agents' rather than 'Mem0 competitor'. Interoperate with per-user memory systems instead of replacing them.

2) ARCHITECTURE: Hybrid vector + bi-temporal knowledge graph (Graphiti's validated fact model: valid_from/valid_to, superseded-not-deleted, provenance to source episodes) + BM25, with structured records mirrored natively (a CRM row should stay a row, not become prose). Default packaging on Postgres+pgvector (Cognee/Memobase proved this maximizes OSS adoption) with pluggable graph/vector backends for scale. Server, not embedded — shared multi-agent memory and permission enforcement both require a server; embedded mode can come later for dev/test.

3) PERMISSIONS AS THE CORE PRIMITIVE (wedge #1): Zanzibar-style ReBAC principal graph (OpenFGA/SpiceDB-compatible), populated by connectors that sync source ACLs (Drive/SharePoint/Salesforce sharing models) alongside content. Enforce by compiling the caller's principal set into a pre-filter on every retrieval — never post-filter, never prompt-level. Add entity/deal-scoping (agent serving customer A cannot retrieve facts tagged to customer B's negotiation) as a first-class scope dimension on top of ACLs. No OSS project does this; it is the hardest feature to retrofit and therefore the moat.

4) FRESHNESS (wedge #2): A connector framework with initial backfill + webhook/CDC incremental sync (Salesforce CDC, HubSpot webhooks, Google Drive changes API, Notion, Zendesk, web-page recrawl), writing through the temporal graph so updates supersede stale facts with full history. Ingestion/consolidation is async (LLM-powered, sleep-time style, per Letta/Zep/Mem0 practice); the read path never waits on it.

5) LATENCY: Target sub-50ms p95 (stretch: 10-30ms) by keeping LLMs entirely out of the read path: in-memory/SSD ANN + inverted index + precomputed scope bitmaps, single-region colocation with the agent runtime. Publish latency-vs-graph-size curves like Zep's sub-200ms/100M-node numbers — that is the bar to beat. Rust or Go for the retrieval hot path; Python acceptable for the ingestion/enrichment pipeline. Expose MCP as the first-class integration surface (multi-tenant, authenticated — 'OpenMemory for organizations') plus a direct REST/gRPC path for inner-loop calls where MCP transport overhead matters.

6) OPEN-CORE SPLIT (learn from Zep's Community Edition failure): one codebase, Apache-2.0, including the real engine, the permission model, and the connector SDK + several reference connectors. Cloud/commercial: managed always-on connector fleet and ACL-sync SLAs, multi-region/HA, SSO/SCIM/audit-log export, usage analytics, and premium connectors. Never withhold the security model from OSS — enterprises won't adopt a memory layer whose permission enforcement they can't inspect.

7) CATEGORY CREATION: Benchmarks now drive adoption (LoCoMo/LongMemEval/BEAM). Publish those, but also define and open-source a 'scoped recall' benchmark measuring permission-leakage rate, cross-tenant isolation, and freshness lag (time from source-system change to retrievability). Nobody measures these today; whoever defines the metric owns the conversation our product is built to win.

## Storage Engine Options

The mid-2026 storage landscape has consolidated around three truths relevant to agent-memory. First, filtered vector search — not raw ANN speed — is the deciding axis, and the ecosystem has finally solved it: Qdrant 1.16 (Nov 2025) shipped ACORN filter-aware HNSW traversal (97.2% recall at 13.9ms on 5M vectors with ~4%-selective filters, vs 53% recall for naive HNSW) plus "tiered multitenancy" that mixes payload-partitioned small tenants with dedicated shards for large ones, promotable with zero downtime; pgvector 0.8's iterative index scans fixed the overfiltering problem in Postgres; and Weaviate's tenant-state model (ACTIVE/INACTIVE/OFFLOADED) handles millions of dormant tenants. Since every agent-memory query carries tenant/scope/entity filters, these engines — not the fastest-unfiltered-QPS leaders — are the relevant shortlist. Object-storage-native designs (Turbopuffer, Milvus 2.6's Woodpecker WAL and tiered storage) have won the cost argument at billion scale, but Turbopuffer's numbers (warm p50 ~14ms, cold p50 ~874ms, ~200ms write commit) show that pattern trades away exactly what an agent's inner loop needs: predictable low-tens-of-ms p99 and instant freshness. It is also proprietary, so it's a design reference and competitor, not a dependency.

Second, the graph-database side is a licensing and continuity minefield. KuzuDB — the leading embedded graph DB — was abandoned in October 2025 when Apple acqui-hired Kùzu Inc (repo archived; community forks Bighorn and LadybugDB are young). Neo4j Community is GPLv3, FalkorDB is SSPLv1, Memgraph is BSL — none is compatible with an Apache-2.0 open-core project's default path. Meanwhile Graphiti (Zep's bi-temporal knowledge graph, Apache 2.0, actively developed through v0.29.2 in June 2026, ~20k stars) has become the reference data model for agent memory — facts with validity intervals, hybrid semantic+BM25+graph retrieval — but it delivers "sub-second," not sub-50ms, latency and requires LLM-in-the-loop ingestion. The right move is to adopt Graphiti's bi-temporal fact model as a schema, not to take a graph-DB dependency: the graph operations agent memory actually needs at query time (entity scoping, 1–2 hop relations, permission edges) are cheap adjacency lookups that a relational store or the vector engine's payload index can serve.

Third, the market has converged on hybrid vector+graph+lexical as the consensus agent-memory architecture (Mem0's 2026 paper, Zep, and Weaviate's Engram managed memory service, GA June 2026 — direct validation and direct competition). Full-text is a solved commodity: Tantivy remains healthy (Apache 2.0, maintained under Datadog post-Quickwit-acquisition), ParadeDB pg_search brings real BM25 into Postgres, and Qdrant/Weaviate ship native sparse/BM25 hybrid fusion. Multimodal storage has a clear winner in the Lance format (v2.2: Blob encoding, ~100x faster random access than Parquet, Apache 2.0, DuckDB integration) as a versioned cold tier on object storage. No single engine covers hot-path scoped retrieval, temporal facts, multimodal blobs, and low-friction adoption — a composed architecture behind one narrow retrieval API is the right call.

### Key findings
- **Qdrant 1.16 (Nov 2025) added tiered multitenancy — payload-partitioned small tenants sharing shards, with zero-downtime promotion of hot tenants to dedicated shards — plus the ACORN algorithm for filter-aware HNSW traversal: 97.2% accuracy at 13.86ms on 5M vectors with two ~4%-selective filters, versus 53.3% accuracy for standard HNSW. Qdrant is Apache 2.0 and reports 20-30ms filtered p99 at 100M vectors.** — _https://qdrant.tech/blog/qdrant-1.16.x/ (Nov 2025); https://www.infoworld.com/article/4099002/qdrant-vector-database-adds-tiered-multitenancy.html_
  - Implication: Qdrant is the only permissively-licensed engine with a first-class answer to our exact hard requirement (every query tenant/scope-filtered, <50ms p99 at 10M+ scale). It should be the primary scale-tier serving engine; our mandatory tenant filter maps directly onto its payload-based multitenancy.
- **Filter-aware indexing is the make-or-break feature, not raw ANN throughput: naive HNSW recall collapses to ~53% under selective filters, and post-filtering either over-fetches or under-returns. pgvector 0.8 added iterative index scans specifically to fix this (up to 100x better result completeness on selective queries), and Qdrant's in-graph filtering is 2-3x faster than post-search filtering.** — _https://www.postgresql.org/about/news/pgvector-080-released-2952/; https://qdrant.tech/blog/qdrant-1.16.x/_
  - Implication: Benchmark candidates only on filtered queries with realistic tenant/scope selectivity. Any storage abstraction we define must push filters into the index (pre-/in-graph filtering), never post-filter in the application layer.
- **Turbopuffer (proprietary, object-storage-native, SPFresh centroid index) serves 4T+ docs and 25k+ QPS with warm p50 ~14ms per 1M-doc namespace — but cold namespace queries are p50 ~874ms and writes take up to ~200ms to commit, one WAL flush per second per namespace.** — _https://turbopuffer.com/docs/architecture; https://turbopuffer.com/blog/turbopuffer_
  - Implication: Object-storage-as-source-of-truth wins on cost and is the right pattern for our durable tier, but its cold-start cliff and write latency are wrong for an agent's inner loop and live-freshness requirement. Treat Turbopuffer as a design reference and managed-cloud competitor, not a dependency (it is closed source).
- **Milvus 2.6 introduced Woodpecker (zero-disk WAL on object storage, replacing Kafka/Pulsar), tiered hot/cold storage, and 72% memory reduction; Milvus 3.0 is targeted late 2026. It is Apache 2.0 and the strongest option at billion scale, but remains a multi-component distributed system (etcd + object storage + coordinators).** — _https://milvus.io/blog/introduce-milvus-2-6-built-for-scale-designed-to-reduce-costs.md; https://milvus.io/docs/roadmap.md_
  - Implication: Milvus is viable for our largest deployments but its operational footprint is too heavy to be the OSS default; requiring users to stand up a Milvus cluster would kill adoption. Keep it as an optional backend at most.
- **KuzuDB, the leading MIT-licensed embedded graph database, was abruptly archived in October 2025 after Apple agreed to acquire Kùzu Inc (confirmed via a Feb 2026 EU DMA filing). Community forks (Bighorn by Kineviz, LadybugDB) exist but are immature. Graphiti has already deprecated its Kuzu backend.** — _https://www.theregister.com/2025/10/14/kuzudb_abandoned/; https://github.com/kuzudb/kuzu_
  - Implication: Cautionary tale: do not make a single-vendor embedded graph engine a load-bearing dependency. Any graph capability in our core should be implemented over storage we control (relational tables / payload indexes) or behind a swappable adapter.
- **Graph database licensing is uniformly hostile to an Apache-2.0 open-core project: Neo4j Community is GPLv3 (and JVM-heavy), FalkorDB is SSPLv1, Memgraph is BSL. FalkorDB/Memgraph deliver sub-millisecond in-memory traversals, but none can sit in our default distribution.** — _https://docs.falkordb.com/license.html; https://memgraph.com/blog/history-of-open-source-licenses-what-license-to-choose; https://arcadedb.com/blog/neo4j-alternatives-in-2026-a-fair-look-at-the-open-source-options/_
  - Implication: We cannot bundle a dedicated graph DB in the OSS core. The graph operations agent memory needs at retrieval time (entity scoping, 1-2 hop relations, permission edges) are cheap adjacency lookups — implement them natively in the primary store rather than adding a second engine with license contamination.
- **Graphiti (Zep, Apache 2.0, v0.29.2 June 2026, ~20k stars) is the reference bi-temporal knowledge-graph model for agent memory: facts carry validity intervals (event time + ingestion time), superseded rather than deleted, with hybrid semantic+BM25+graph retrieval. But its retrieval is 'sub-second', not sub-50ms, and ingestion requires an LLM in the loop; backends are Neo4j/FalkorDB/Neptune.** — _https://github.com/getzep/graphiti; https://arxiv.org/abs/2501.13956_
  - Implication: Adopt Graphiti's bi-temporal fact schema (valid_from/valid_to/superseded_by) as our data model for entity facts — it directly solves 'pricing quoted to customer A last month vs updated yesterday'. But implement it natively on our own storage for latency; optionally offer a Graphiti-compatible import/adapter.
- **The 'one Postgres' stack is now credible to roughly 10M vectors: pgvector 0.8 (iterative scans, parallel HNSW builds) + pgvectorscale StreamingDiskANN + ParadeDB pg_search (Tantivy-based BM25, v0.22.5 Apr 2026) give dense+lexical hybrid search with RRF, real transactional consistency, and trivial CDC — and multiple sources note teams migrating back to Postgres in 2026.** — _https://www.postgresql.org/about/news/pgvector-080-released-2952/; https://www.paradedb.com/blog/hybrid-search-in-postgresql-the-missing-manual; https://pgxn.org/dist/pg_search/_
  - Implication: Postgres should be our zero-friction default backend: one container, transactional writes (freshness for free), tenant filters as WHERE clauses with B-tree indexes. Scoped p99 <50ms is achievable at single-digit-millions scale per deployment; direct users beyond that to the Qdrant profile.
- **Weaviate (BSD-3) launched Engram in June 2026 — a GA managed 'memory and context service for agentic AI' with async ingestion pipelines writing back into multi-tenant Weaviate — and Mem0's April 2026 paper formalized the consensus agent-memory architecture: hybrid vector similarity + knowledge-graph traversal + key-value scopes (user/session/agent).** — _https://www.opensourceforu.com/2026/06/weaviate-launches-engram-to-provide-production-grade-memory/; https://mem0.ai/blog/graph-memory-solutions-ai-agents; https://weaviate.io/blog/weaviate-multi-tenancy-architecture-explained_
  - Implication: Direct market validation and direct competition: incumbents are moving from 'vector DB' to 'memory service'. Our differentiation must be the parts they lack — permission-aware scoping from source systems of record, CDC freshness, and framework-agnostic MCP access — not the vector index itself. The vector+graph+lexical hybrid is table stakes.
- **Chroma completed its Rust-core rewrite (~4x faster) but remains comfortable only to ~5-10M vectors on a single node with RAM-resident HNSW; its distributed version is cloud-oriented. Typesense (GPL-3) is fully in-memory; Meilisearch (MIT) gates sharding behind Enterprise Edition.** — _https://docs.trychroma.com/guides/performance/single-node; https://typesense.org/docs/overview/comparison-with-alternatives.html; https://www.meilisearch.com/docs/resources/comparisons/typesense_
  - Implication: None of these can be the enterprise-scale core. One pattern worth stealing: Typesense's scoped API keys (HMAC-signed tokens embedding non-overridable filters) is an elegant enforcement mechanism for permission-scoped retrieval — issue agents scoped tokens whose tenant/entity filters cannot be bypassed.
- **Lance format 2.2 (Apache 2.0) added Blob V2 encoding, nested schema evolution, and native multimodal storage (images/audio/video/embeddings in one format) with ~100x faster random access than Parquet, data versioning/time-travel, and a DuckDB extension (May 2026); LanceDB is embeddable with no server required. Tantivy remains a safe Apache-2.0/MIT full-text library, actively maintained after Datadog's Quickwit acquisition (Jan 2025) with Quickwit relicensed Apache 2.0.** — _https://docs.lancedb.com/lance; https://duckdb.org/2026/05/21/test-driving-lance; https://quickwit.io/blog/quickwit-joins-datadog_
  - Implication: Use Lance on object storage as our multimodal, versioned durable tier (raw docs, transcripts, images, embedding lineage, re-embedding jobs), decoupled from the hot serving index. If we build a Rust core, Tantivy is the proven embedded lexical-search component.
- **Redis 8 (AGPLv3 option restored, 2025) added native vector sets and is widely used as the millisecond hot tier for agent memory — session state, LangGraph checkpointers, semantic caching — though its precision/latency tradeoffs at billion scale (200ms median at 90% precision on 1B vectors) rule it out as the primary retrieval index.** — _https://redis.io/blog/redis-8-ga/; https://redis.io/blog/searching-1-billion-vectors-with-redis-8/; https://redis.io/blog/long-term-memory-architectures-ai-agents/_
  - Implication: Optional hot tier only: working/session memory and semantic cache in front of the retrieval engine, not the system of record. AGPL is acceptable as an optional external service dependency but should not be linked into our core.

### Recommendations
Recommend a COMPOSED architecture behind one narrow retrieval API — no single engine covers scoped low-latency retrieval, temporal facts, multimodal blobs, and low-friction adoption — but composed of few parts, with pluggable backends at exactly one seam.

1) Architecture: three tiers. (a) SERVING TIER (the <50ms path): one hybrid index holding dense vectors + sparse/BM25 + payload-indexed scope metadata, where every record carries tenant_id / entity_ids / acl_tags / valid_from / valid_to and every query MUST carry scope filters pushed into the index (in-graph filtering, never post-filtering). (b) DURABLE TIER: Lance format on object storage (Apache 2.0) as the versioned, multimodal source-of-truth corpus — raw docs, images, transcripts, embedding lineage, time-travel — feeding the serving tier asynchronously. (c) Optional HOT TIER: Redis/Valkey for session/working memory and semantic cache.

2) Backends: ship two reference profiles behind a storage-adapter trait. DEFAULT PROFILE = Postgres (pgvector 0.8 + pgvectorscale + ParadeDB pg_search): one container, transactional freshness, hybrid dense+BM25 via RRF, scope filters as indexed WHERE clauses; honest ceiling ~5-10M vectors per deployment. SCALE PROFILE = Qdrant (Apache 2.0): tiered multitenancy, ACORN filtered HNSW (~14ms at 4% filter selectivity on 5M vectors; 20-30ms filtered p99 reported at 100M), native sparse vectors for hybrid, incremental upserts for CDC-driven freshness. Do NOT default to Milvus (ops-heavy), Chroma (scale ceiling), or Turbopuffer/object-storage-native serving (cold-start cliff, ~200ms write commit — wrong for inner-loop freshness; also proprietary).

3) Graph/temporal: do NOT take a graph-database dependency. Neo4j (GPLv3), FalkorDB (SSPLv1), Memgraph (BSL) are license-incompatible with an Apache-2.0 core, and the KuzuDB abandonment (Apple acqui-hire, Oct 2025) shows the risk of embedded-graph bets. Instead, adopt Graphiti's bi-temporal fact model as a SCHEMA — entities, relations, and facts with valid_from/valid_to/superseded_by — stored as rows/payloads in the primary backend. The graph ops agent memory needs at query time are entity scoping and 1-2 hop expansion: cheap adjacency lookups, fine in Postgres or Qdrant payloads. Offer an optional Neo4j/FalkorDB adapter for deep-traversal analytics, out of the hot path.

4) Scoping enforcement: make scope a protocol-level guarantee, not a query convention. Issue agents scoped credentials (Typesense-style HMAC scoped keys / signed MCP session context) that bind non-overridable tenant/entity/ACL filters server-side, so an agent talking to customer A physically cannot query customer B's memory.

5) Freshness: CDC/webhook events flow through a small ingest log into (a) direct upsert to the serving tier (Qdrant/pgvector handle incremental updates in milliseconds-to-seconds) and (b) append to Lance for durability/versioning. Target sub-second source-change-to-queryable for structured records; seconds for re-embedded documents.

6) Language/runtime and open-core split: Rust core (matches Qdrant, Lance, Tantivy ecosystem; embeds Tantivy if we later internalize lexical search). OSS (Apache 2.0): the memory server, Postgres + Qdrant adapters, bi-temporal schema, MCP interface, scoped-credential enforcement, single-tenant/small-cluster operation. CLOUD: massive multi-tenant operation (tiered tenant placement, tenant promotion, object-storage tiering a la Turbopuffer/Milvus 2.6), managed CDC connectors (Salesforce/Zendesk/Notion/web crawl), cross-region replication, audit/compliance. This mirrors where Qdrant, Weaviate, and Milvus themselves draw the OSS/cloud line — and note Weaviate Engram (GA June 2026) confirms the managed-memory market while leaving the permission-aware, CDC-fresh, framework-agnostic slice open.

## Real-Time Freshness & Ingestion

Keeping an enterprise memory layer fresh in mid-2026 is a solved-in-pieces problem: no single tool covers "database CDC + SaaS webhooks + polling fallback + incremental re-embedding + derived-memory invalidation," which is exactly the gap agent-memory can own. For databases, log-based CDC is mature and fast (Debezium 3.5/3.6 is the enterprise standard; PeerDB, now ClickHouse-owned but still ELv2 open source, is the high-throughput Postgres specialist; Sequin — the lightweight Kafka-free option — had its cloud shut down in Oct 2025 and its MIT-licensed OSS is in maintenance mode, a cautionary tale about depending on venture-backed CDC startups). For SaaS sources, the event surface is uneven: Salesforce CDC over the gRPC Pub/Sub API delivers change events in ~1–2 seconds (with 72-hour replay and a 5-entity limit without add-on license), HubSpot v4 webhooks deliver in under 5 seconds with a journal API for resumable ordered consumption, Notion finally shipped API webhooks (but they don't fire on block-level content edits, so polling is still required for page bodies), and Google Drive push channels expire in ≤7 days with no auto-renewal — every serious system pairs webhooks with periodic reconciliation polling because push delivery is explicitly lossy.

The reference architectures from incumbents confirm the pattern. Glean uses a three-tier freshness model: webhooks where available (updates in ~5 minutes), incremental crawls (hourly-ish per connector), and full crawls (6 hours to 28 days) as the consistency backstop for deletions and permission drift. Dust runs every connector event (Slack message, Notion edit, GitHub PR) through Temporal workflows that handle ingest → chunk → embed → index asynchronously with retries — durable-execution orchestration, not cron. On the re-indexing side, the emerging consensus is to treat embeddings as incrementally-maintained derived data: chunk-level content hashing so only changed chunks are re-embedded, embedding caches keyed by (content hash, model, params), and lineage tracking so stale derived rows can be precisely deleted. CocoIndex (Rust core, open source) is the most direct embodiment — dataflow-style incremental recomputation with end-to-end lineage, claiming ~10x cost reduction at scale — and Graphiti/Zep demonstrates the right pattern for derived facts: bi-temporal edges (t_valid/t_invalid) that are invalidated-not-deleted when superseded, which is what agent-memory needs for summaries and extracted facts whose sources change. The "opportunity updated in Salesforce → agent sees it in <1 minute" target is comfortably achievable: ~1–2s for the CDC event, sub-second for structured-field upsert, and a few seconds for re-embedding only the affected chunks; the hard engineering is the invalidation cascade (marking derived summaries stale synchronously, recomputing them lazily/asynchronously) and the polling reconciliation loop that catches what webhooks drop.

- **Serving-layer freshness is no longer the bottleneck: Qdrant (Rust HNSW) benchmarks at ~4ms p50 with real-time upserts; Turbopuffer does sub-10ms p50 on object storage at ~100x lower storage cost; Milvus handles high-churn insert/delete without disruptive reindexing. ### Recommendations
1) Architect freshness as a two-lane, per-connector system: a push lane (Salesforce Pub/Sub gRPC, HubSpot v4 webhooks + journal, Slack Events, Drive changes.watch, Notion webhooks, Debezium-format CDC for databases) and a reconciliation lane (cursor-based incremental polls every 5–60 min, full crawls on Glean-style 6h–28d schedules for deletion/permission cleanup). Treat webhooks as an optimization, never as truth — every push source gets a polling backstop because delivery is documented-lossy and Drive channels expire without renewal.

2) Own 5–8 flagship connectors natively (Salesforce, Google Drive, Slack, Notion, HubSpot, Confluence, Postgres-via-CDC, generic web crawl) where sub-minute freshness and permission metadata are the product; delegate the long tail to Nango (OSS-compatible, 30s polling, webhook syncs) behind a pluggable adapter interface. Accept Debezium change-event envelopes as a first-class input so customers with existing Kafka/Debezium infra plug in directly. Do not depend hard on any single CDC startup (Sequin's shutdown is the lesson).

3) Split memory into two stores with different freshness mechanics: (a) structured/record memory (CRM fields, ticket status) updated transactionally on the CDC event with zero embedding work — this alone satisfies 'opportunity updated → agent sees new value in <5 seconds' via entity lookup; (b) semantic/vector memory updated via chunk-level incremental re-embedding. Pipeline: stable chunk IDs, content-hash diffing, embedding cache keyed on (hash, model, params), and end-to-end lineage from every index row and derived memory back to (source, record, version) — CocoIndex is the reference design and a candidate component.

4) Handle derived-memory invalidation with lineage + bi-temporal staleness: on source change, synchronously walk lineage to mark dependent summaries/extracted facts STALE (with superseded_at timestamps, Graphiti-style invalidate-don't-delete), and recompute asynchronously. Expose staleness metadata in the retrieval API (last_synced_at, is_stale, source_version) so agents and evals can reason about freshness; publish per-connector freshness SLOs (p50/p95 event-to-queryable) as a headline product metric — nobody in the market does this and it's cheap credibility.

5) Run the entire ingest/refresh plane on durable execution (Temporal or an OSS equivalent), following Dust: one workflow per change event handling fetch-enrich-chunk-embed-index with retries, rate-limit backpressure, and replay-ID checkpointing. Keep the ingest plane server-side and horizontally scalable (this rules out embedded-only architecture for ingestion, whatever the serving layer decision); the serving layer can then be Qdrant/Turbopuffer/pgvector-class tech where 4–10ms p50 already meets the low-tens-of-ms retrieval target. Open-core split suggestion from this research: OSS gets the freshness engine, connector SDK, and flagship connectors; cloud gets managed webhook endpoints/verification, hosted durable execution at scale, cross-tenant connector fleet monitoring, and freshness SLO dashboards.

## Permission-Aware & Context-Scoped Retrieval

Permission-aware retrieval in mid-2026 has converged on a clear industry pattern, best exemplified by Glean and Onyx: connectors ingest each document's ACL alongside its content, ACL principals (users/groups) are materialized as metadata on indexed chunks, group membership is resolved per-user at query time, and the retrieval engine applies the resulting principal set as a mandatory filter inside the ANN/hybrid search — never as a post-generation check. Glean markets exactly this (query-time enforcement over a permissions-aware knowledge graph with an identity/permissions store that expands the user's groups, then filters the index); Onyx (ex-Danswer, open source) mirrors source ACLs into an access_control_list field in Vespa on permission-sync cycles and filters hybrid (vector+BM25) retrieval on it; Dust uses a coarser but instructive model — Spaces as hard data partitions, each agent bound to a space, with a dual-layer rule that an agent's users must by default have access to all spaces the agent reads from. The critical performance enabler is that filtered vector search is now a solved problem in modern engines: Qdrant's filterable HNSW (+ACORN in v1.16), Weaviate's ACORN, and Pinecone's single-stage integrated filtering keep recall and latency stable under selective filters (benchmarks show integrated-filter engines gaining ~1.2–1.5x throughput under 10% filters, while post-filtering engines like pgvector/OpenSearch spike to 200–300ms). Turbopuffer demonstrates the complementary hard-partition pattern: namespace-per-tenant at 250M+ namespaces with ~8ms p50 warm queries, with tenant isolation enforced by namespace selection rather than filters.

The ReBAC ecosystem (SpiceDB, OpenFGA, Cerbos, Oso) has first-class RAG integration guidance, and all vendors frame the same three patterns: (1) pre-filter — call LookupResources/ListObjects to get the user's authorized ID set and pass it as a vector-store filter (best when users see a small slice of the corpus); (2) post-filter — retrieve then BatchCheck the top-k (best when users see most documents; cheap because k is small); (3) sync — materialize permissions into the search index and use the ReBAC store as source of truth. The key performance caveat, documented by AuthZed themselves, is that unbounded LookupResources over large accessible sets, complex schemas, or intersections/exclusions "will always perform poorly" — so pure query-time ReBAC pre-filtering does not fit a low-tens-of-ms budget at millions of documents. The fast pattern is the Glean/Onyx one: materialize ACL tokens into the index (kept fresh by CDC from the ReBAC store), cache the subject→principal-set expansion, and optionally re-verify only the top-k results against the live ReBAC store to close the staleness window.

The scoping problem beyond ACLs ("agent may read both customers, but must not surface B's pricing to A") is now recognized in the research literature as a contextual-integrity problem and is demonstrably NOT solvable by prompting: CIMemories (ICLR 2026) shows frontier models leak up to 69% of inappropriate attributes from persistent memory, violations accumulate over multi-task sessions, and privacy prompting fails — the authors conclude enforcement must be architectural. The strongest prior art is AirGapAgent (Google, CCS 2024): a contextual-integrity data-minimization layer that restricts which memory even reaches the model based on the task context, so injection or model error cannot exfiltrate out-of-context data. Memory products (Mem0, Zep, Letta) implement a weaker version via composite namespacing (user_id/agent_id/run_id/app_id scopes composed at retrieval). Meanwhile the identity substrate matured in June 2026: MCP's Enterprise-Managed Authorization extension went spec-stable, built on ID-JAG (Okta's Cross App Access), giving memory servers standardized on-behalf-of tokens with sub/azp/act claims — meaning a memory layer can now know cryptographically both which human and which agent a query is for. The recommended model is therefore a three-plane design: a ReBAC source of truth, materialized ACL-token enforcement inside filtered ANN, and a deterministic scope/purpose-binding layer (tenant namespace + mandatory entity-scope filter + provenance-based context policy) evaluated before the model ever sees a memory.

  - Implication: We should not build our own authorization model — adopt Zanzibar-style ReBAC (SpiceDB or OpenFGA, both OSS) as the policy source of truth and implement both pre- and post-filter adapters, selected by estimated selectivity.
- **Pure query-time ReBAC pre-filtering does not fit a tens-of-ms budget at scale: AuthZed's own docs state LookupResources gets slow with large relation datasets, complex schemas, or large accessible-result sets; 'unbounded LookupResources with large numbers of reachable permissions will always perform poorly,' and intersections/exclusions force candidate-set computation plus per-candidate checks.** — _https://authzed.com/docs/spicedb/ops/performance ; https://linen.authzed.com/t/18812850/lookupresources-performances (accessed 2026-07-09)_
  - Implication: For millions of entities, the authorized-ID set must be materialized into the index ahead of time (ACL tokens on chunks/entities, updated via the ReBAC store's Watch/changelog API), with the live ReBAC engine used only for (a) subject→principal expansion (cacheable) and (b) optional top-k recheck. Query-time LookupResources is only viable for small scopes.
- **Cerbos and Oso offer the ABAC/policy-compilation alternative: Cerbos query plans partially evaluate policy and emit residual conditions translated into native filters for Pinecone, Weaviate, Chroma, Qdrant, FAISS, applied as a pre-filter; Oso's listLocal() converts centralized authorization facts into local SQL WHERE clauses, and Oso stresses that adding LIMIT-k before authorization breaks the guarantee — authorization must be inside the retrieval query.** — _https://docs.cerbos.dev/cerbos/latest/recipes/ai/rag-authorization/ ; https://www.cerbos.dev/blog/filtering-database-results-with-cerbos-query-plans ; https://www.osohq.com/post/authorizing-llm (accessed 2026-07-09)_
  - Implication: Policy-to-filter compilation is the right mechanism for attribute-based scope rules (region, confidentiality class, deal stage) that don't fit relationship tuples; our filter model should accept both materialized ACL tokens (ReBAC) and compiled predicate filters (ABAC). Also confirms the invariant: the scope filter must be part of the ANN query, never applied after truncation to top-k.
- **Filtered vector search is no longer a latency tax on engines with in-algorithm filtering: Qdrant's filterable HNSW builds extra graph links and adaptively chooses brute-force vs graph traversal by filter selectivity, and Qdrant 1.16 (2025) added ACORN (neighbor-of-neighbor expansion) plus tiered multitenancy; Weaviate uses ACORN two-hop expansion with flat-scan fallback on tiny subsets. Benchmarks show integrated-filter engines (Pinecone p2, Zilliz) gain ~1.2–1.5x throughput under 10%-selective filters, while post-filtering stacks (pgvector, OpenSearch, LanceDB) spike to 200–300ms; selective filters can actually reduce tail latency by 10–30ms.** — _https://qdrant.tech/blog/qdrant-1.16.x/ ; https://yudhiesh.github.io/2025/05/09/the-achilles-heel-of-vector-search-filters/ ; https://qdrant.tech/benchmarks/ (accessed 2026-07-09)_
  - Implication: Mandatory ACL/scope filters inside the ANN query are compatible with a 10–30ms retrieval budget IF we choose an engine with native filterable indexing (Qdrant-class) or implement filter-aware HNSW/ACORN ourselves. Post-filter-only engines are disqualified for the core index.
- **Turbopuffer proves namespace-per-tenant hard partitioning at extreme scale: object-storage-backed namespaces as the unit of isolation, 250M+ namespaces observed in production, ~8ms p50 warm queries (343ms cold on a 1M-doc namespace); it has no namespace-level ACL API — isolation is enforced by the application mapping the authenticated session to a namespace. Low-selectivity filters (>50% of corpus) still degrade ANN quality.** — _https://turbopuffer.com/docs/architecture ; https://turbopuffer.com/docs/tradeoffs (accessed 2026-07-09)_
  - Implication: Tenant isolation should be physical (namespace/collection per tenant), not a filter — filters are for intra-tenant ACL and entity scoping. The cold-start number also warns us: per-entity micro-partitions would be too cold; entity scoping belongs in filters within a tenant partition, with hard partitions reserved for tenants.
- **CIMemories (arXiv:2511.14937, accepted ICLR 2026) benchmarks contextual integrity of persistent LLM memory: frontier models show up to 69% attribute-level violations (surfacing memory attributes inappropriate for the task context), violations accumulate across tasks (GPT-5: 0.1%→9.6% over 40 tasks), behavior is unstable across identical runs (up to 25.1% variance), models overgeneralize to share-everything-or-nothing, and privacy-conscious prompting does not fix it.** — _https://arxiv.org/abs/2511.14937 (accessed 2026-07-09)_
  - Implication: Direct experimental proof that our customer-A/customer-B scoping requirement cannot be delegated to the model or the prompt. Scoping must be enforced deterministically in the retrieval layer — the model should never receive out-of-scope memory in the first place.
- **AirGapAgent (Google DeepMind, ACM CCS 2024) is the canonical prior art for contextual-integrity-based agent memory scoping: a data-minimization module selects the minimal subset of user data relevant to the current task context BEFORE the conversational model runs, so adversarial third parties manipulating the conversation cannot induce the agent to reveal data outside the minimized set — the agent is 'air-gapped' from out-of-context memory. Grounded explicitly in Nissenbaum's contextual integrity (appropriate information flows per context norms). Follow-on work (e.g., 'Contextual Integrity in LLMs via Reasoning and RL', arXiv:2506.04245; PrivacyAlign) extends CI reasoning but keeps the same architectural insight.** — _https://arxiv.org/abs/2405.05175 ; https://dl.acm.org/doi/abs/10.1145/3658644.3690350 ; https://arxiv.org/pdf/2506.04245 (accessed 2026-07-09)_
  - Implication: Our purpose-binding design should follow AirGapAgent's structure: an interaction context (customer entity, task purpose) declared at session start deterministically gates which memory partitions/classes are retrievable for the whole session — minimization at retrieval, not redaction at generation. This is also robust to prompt injection.
- **Current agent-memory products implement scoping as composite namespacing, not authorization: Mem0 scopes writes/reads by user_id + agent_id + run_id (+ app_id), returning the union matching whatever IDs the caller passes, with identity derived from application-level auth; Zep and Letta are similar. None enforce document-level ACLs from source systems or purpose binding.** — _https://mem0.ai/blog/state-of-ai-agent-memory-2026 ; https://agentmarketcap.ai/blog/2026/04/10/agent-memory-vendor-landscape-2026-letta-zep-mem0-langmem (accessed 2026-07-09)_
  - Implication: Good API-shape prior art (scope keys on every read/write call) but a competitive gap: no OSS memory layer today combines source-ACL inheritance + ReBAC + entity/purpose scoping. Our scoped-read API should make scope parameters mandatory and server-enforced (fail-closed), not caller-optional filters.
- **The agent-identity substrate standardized in June 2026: MCP's Enterprise-Managed Authorization (EMA) extension went spec-stable (2026-06-18), built on the IETF Identity-Assertion JWT Authorization Grant (ID-JAG, marketed by Okta as Cross App Access/XAA). IdP-mediated delegation replaces per-user OAuth consent; tokens carry sub (end user), azp (agent/client), aud, and act claims so downstream services know both who initiated a request and which agent acts on whose behalf. Anthropic, VS Code, Okta and ~9 MCP servers shipped support at launch.** — _https://thenewstack.io/mcp-gets-its-missing-enterprise-authorization-layer/ ; https://developer.okta.com/blog/2025/09/03/cross-app-access ; https://www.okta.com/newsroom/articles/cross-app-access-extends-mcp-to-bring-enterprise-grade-security-to-ai-agents/ (accessed 2026-07-09)_
  - Implication: Our MCP-first memory server should consume EMA/ID-JAG tokens natively: the (user, agent, on-behalf-of chain) tuple from the token becomes the authorization subject, and the declared task/session context becomes the scope key. This removes the need to invent our own agent-identity scheme and is the enterprise-credible answer to 'which principal is querying memory?'

### Recommendations
Adopt a three-plane model: (1) AUTHORIZATION PLANE — embed a Zanzibar-style ReBAC engine as the policy source of truth (recommend OpenFGA for permissive Apache-2.0 licensing and ecosystem breadth, or SpiceDB for Zanzibar fidelity/consistency; both are OSS). Connectors ingest ACLs with content (Glean/Onyx pattern) and write relationship tuples; permission changes flow through the same CDC/webhook pipeline as content changes, targeting seconds-level freshness rather than Onyx-style periodic sync. (2) ENFORCEMENT PLANE — do NOT call the ReBAC engine's ListObjects/LookupResources on the hot path at scale; materialize per-item 'visibility tokens' (allowed principals/groups + tenant + entity tags + confidentiality class) as metadata in the index, kept fresh via the ReBAC Watch/changelog stream. At query time: resolve the subject (from the MCP EMA/ID-JAG token: user sub + agent azp + act chain) to a cached principal set (sub-ms to low-ms with a short-TTL cache), and attach it as a MANDATORY filter inside the ANN query. This requires an engine with in-algorithm filtering — Qdrant-class filterable HNSW/ACORN — so budget is roughly: principal-cache lookup 1–2ms + filtered ANN 5–20ms. For high-sensitivity classes, add an optional top-k BatchCheck against the live ReBAC store (~3–10ms for k≤50) to close the materialization-staleness window. Fail closed: an item with no visibility tokens, or a query with no resolvable subject, returns nothing. (3) SCOPE PLANE (the beyond-ACL layer) — every read carries a server-enforced MemoryScope object, not caller-optional filters: tenant_id maps to a physical partition (namespace/collection per tenant, Turbopuffer-style — never a mere filter); entity_scope (e.g., customer/account ID) is a mandatory filter for interaction-bound sessions, derived from provenance tags stamped on every memory item at write time (source system, source entity, confidentiality class); purpose binding follows AirGapAgent — the session declares a context (entity + task purpose) once, a deterministic policy (Cerbos-style compiled predicates work well here) maps that context to the set of retrievable provenance/confidentiality classes, and that gate holds for the whole session regardless of what the conversation (or an injected prompt) asks for. CIMemories proves the model cannot be trusted to withhold, so cross-entity data (customer B's pricing) must never enter the context window during a customer-A-scoped session; agents needing cross-entity analytics must open an explicitly different, audited scope. API design: make scope parameters required on the MCP retrieval tool signature; log every (subject, scope, results) tuple for audit. OSS/commercial split: keep the ENTIRE enforcement and scoping path in the OSS core (a permission layer that is partly paywalled, like Onyx EE, undermines trust and is our differentiation opportunity); monetize managed connectors/permission-sync at scale, IdP integrations (XAA/ID-JAG turnkey), audit/compliance reporting, and hosted multi-region operation.

## Cross-Framework Interop & MCP

As of mid-2026, MCP has decisively won as the cross-framework interop layer for agent context: it is Linux Foundation-governed (donated Dec 2025, co-sponsored by OpenAI, Google, Microsoft), has ~10-20K public servers and ~97M monthly SDK downloads, and every major agent client speaks it. The critical architectural news is the 2026-07-28 release candidate (final publication July 28, 2026), which makes MCP stateless-first: the initialize handshake and Mcp-Session-Id are removed, servers must use explicit server-minted handles for cross-call state, resources/subscribe is replaced by a unified subscriptions/listen long-lived stream, list/read results gain ttlMs/cacheScope caching hints, and a formal Extensions framework (with Tasks and MCP Apps as the first official extensions) plus deprecation policy arrive. A memory layer built today should target this stateless model from day one — it maps perfectly onto a horizontally-scaled, low-latency retrieval service. However, MCP alone is not sufficient: it is the agent-facing read/write interface, not the ingestion or framework-embedding interface.

Framework-native memory interfaces have NOT converged on a standard, but they have converged on a pattern: a small pluggable interface with a handful of verbs, into which third-party memory backends slot. LangGraph's BaseStore exposes get/put/delete/search over JSON docs in hierarchical namespaces; Microsoft Agent Framework 1.0 (the AutoGen+Semantic Kernel unification, GA April 2026) defines a Memory protocol (add/query/update_context/clear) with Neo4j, Mem0, Redis, and Foundry as launch providers; CrewAI has an ExternalMemory provider slot; Google ADK has MemoryService (backed by Vertex AI Memory Bank); OpenAI Agents SDK has Sessions with pluggable backends but no cross-session semantic memory (a gap third parties fill); Claude Agent SDK's memory_20250818 tool is client-side file operations whose storage backend you control; AWS AgentCore Memory offers events + extraction strategies + namespaces. Mem0 and Zep have proven the winning go-to-market: one core service, thin adapters into every framework's plug point, plus an MCP server. Emerging "memory standards" (Agent Memory Protocol v0.1, Open Memory Protocol, the W3C AI Agent Memory Interoperability Community Group proposed May 2026) are all nascent single-vendor or draft efforts — worth tracking, not worth betting on.

On operations and writes: the ecosystem has converged on a small verb set — remember (add with extraction), recall (scoped semantic/graph search), get/list, update, forget (delete), plus two differentiators: pinned always-in-context memory (Letta's shared memory blocks, which multiple agents attach to and see updates immediately) and subscribe-to-changes (now protocol-supported via MCP subscriptions/listen). For agent write-back, the state of the art is Mem0's LLM-arbitrated reconciliation (ADD/UPDATE/DELETE/NOOP decided against top-K similar existing memories) and Zep/Graphiti's bi-temporal model (every fact carries t_valid/t_invalid plus created/expired system timestamps; conflicting facts are invalidated, never destroyed, and every fact traces to its source episode). Trust of agent-written facts is now a first-class security topic: memory poisoning is OWASP's ASI06 top agentic risk for 2026, MINJA-style attacks show >95% injection success against production agents, and the emerging defense pattern is mandatory provenance fields (created_by, source, trust score, provenance chain), partitioning agent-written observations from system-of-record-derived facts, and trust-weighted retrieval.

### Recommendations
1) API surface: ship three layers. (a) An MCP server targeting the stateless 2026-07-28 spec as the universal agent-facing interface — this alone covers ChatGPT, Claude, Gemini, and every MCP-capable framework. (b) A REST (+optional gRPC) API as the substrate: high-throughput ingestion/CDC, admin, bulk ops, and the thing the MCP server itself calls. (c) Thin native adapter packages implementing each framework's documented plug point: LangGraph BaseStore, CrewAI ExternalMemory provider, Microsoft Agent Framework Memory provider, Google ADK MemoryService, OpenAI Agents SDK Session backend, and a Claude Agent SDK memory-tool storage backend. This adapter strategy is exactly how Mem0 and Zep won distribution; the plug points are small and stable.

2) Operations: keep the agent-facing verb set minimal — recall (scoped hybrid search, the hot path, must hit low tens of ms), remember (fast append of an observation/episode; extraction and reconciliation happen async), forget (with audit trail and compliance semantics), pin/unpin (Letta-style always-in-context memory blocks per agent/entity, updated live by CDC — the best answer to inner-loop latency), and subscribe (MCP subscriptions/listen for MCP clients, webhooks/SSE on REST). Expose consolidation/compaction as a background service concern, never an agent-facing call. Use ttlMs/cacheScope caching hints aggressively on entity reads.

3) Scoping: enforce all tenant/entity/permission scoping server-side from the authenticated principal (OAuth per the hardened MCP auth model; align agent identity with A2A signed Agent Cards). Namespace paths (tenant/actor/entity/context) as in LangGraph BaseStore and AgentCore are the right addressing model. Never accept agent-supplied tenant or customer IDs as authorization inputs — this is the mechanism that prevents 'customer B pricing leaks to customer A'.

4) Writes: adopt a two-tier trust model as a core design pillar. Tier 1: facts derived from systems of record via CDC — authoritative, agents cannot overwrite them. Tier 2: agent-written observations — append-only proposals carrying mandatory provenance (writer agent identity, source, timestamps, provenance chain), reconciled asynchronously via Mem0-style ADD/UPDATE/DELETE/NOOP arbitration, stored with Graphiti-style bi-temporal validity (invalidate, never destroy). Rank recall results by trust tier and recency. Memory poisoning is OWASP ASI06 in 2026; making provenance and tiered trust native is both a security necessity and the clearest enterprise differentiator versus Mem0/Zep/hyperscaler memory banks, which are conversation-centric and single-writer.

5) Standards posture: build MCP-first, ignore AMP/OMP for now, join/monitor the W3C AI Agent Memory Interoperability CG, and design the REST schema cleanly enough to propose as a reference model if that group gains traction. Bi-temporal provenance-carrying facts (Zep-validated: 63.8% vs 49.0% LongMemEval on temporal queries) also give the architecture team a concrete signal favoring a temporal-knowledge-graph-plus-vector hybrid over pure vector storage.

## Multimodal Memory

The multimodal embedding landscape in mid-2026 has matured into three distinct architectural camps, and the right answer for agent-memory is to support all three behind one abstraction, staged over time. Camp 1 is "text-first": extract/transcribe/describe everything into text, embed with a text model. Camp 2 is "native multimodal single-vector": Cohere embed-v4.0 (128k context, mixed text+image+PDF inputs, 256-1536 Matryoshka dims), voyage-multimodal-3.5 (Jan 2026, interleaved text/image/video, 256-2048 dims, quantization-aware), Google Gemini Embedding 2 (Mar 2026, all-modality), and open-weight Jina embeddings v4 (3.8B, Qwen2.5-VL-based, dense AND multi-vector modes) embed page screenshots and images directly into the same vector space as text — eliminating OCR pipelines and beating describe-then-embed by ~20-32% on retrieval metrics (nDCG@5/mAP@5) in controlled studies. Camp 3 is late-interaction (ColPali lineage, now ColQwen3-4B at the ViDoRe frontier, and ColModernVBERT at 250M params within 0.6 nDCG points of ColPali): highest accuracy on visually rich documents, but ~1,024 patch vectors per page makes storage and MaxSim latency 2-3 orders of magnitude heavier than single-vector — fundamentally at odds with a "low tens of milliseconds inner-loop" target unless confined to a rerank stage or compressed via MUVERA-style fixed dimensional encodings (which recover single-vector MIPS speed with ~10% better recall and 90% lower latency vs prior multi-vector heuristics; now implemented in Qdrant and Weaviate).

The BYO-key constraint is decisive: OpenAI — the key most users actually have — still has NO multimodal embedding model (text-embedding-3 is unchanged since 2023), so an OSS project that requires multimodal embeddings would exclude the largest key population. That forces a text-first canonical representation at launch: every memory item, regardless of source modality, carries a text "surface form" (extracted text, ASR transcript with speaker/timestamp structure, or VLM-generated description) embedded with whatever text model the user's key supports, plus a durable pointer to the original media. Document parsing is a solved-enough commodity (Docling is the strongest OSS option, ~0.88 on opendataloader-bench, with commercial Reducto/LlamaParse/Unstructured above it; all benchmarks are vendor-published, none neutral), and ASR is similarly commoditized (Whisper large-v4, Deepgram Nova-3/4 at ~300-450ms streaming, AssemblyAI Universal-3 with built-in diarization) — both belong at the ingestion edge as pluggable adapters, never in the retrieval core. Competitively, Cognee is the only agent-memory incumbent with serious multimodal ingestion (30+ connectors incl. audio auto-transcription and image OCR+caption); Mem0/Zep/Letta remain text-centric, so a well-designed multimodal story is genuine differentiation rather than table stakes.

### Key findings
- **Cohere embed-v4.0 is the most enterprise-ready hosted multimodal embedder: text, images, and mixed text/image (PDF pages) in one model, 128k-token context, Matryoshka dims 256/512/1024/1536.** — _https://docs.cohere.com/docs/cohere-embed (fetched 2026-07-09)_
  - Implication: A single-vector multimodal path can be added without changing index structure — one dense vector per page/image, same HNSW index and same latency profile as text. Make embed-v4 the reference 'native multimodal' provider.
- **voyage-multimodal-3.5 (Jan 15, 2026, Voyage AI/MongoDB) embeds interleaved text+images+video frames, with Matryoshka dims 2048/1024/512/256 and quantization-aware training; Gemini Embedding 2 (Mar 2026) is Google's first all-modality model.** — _https://blog.voyageai.com/2026/01/15/new-models-and-expanded-availability/ ; https://www.mongodb.com/docs/voyageai/models/multimodal-embeddings/_
  - Implication: At least three hosted BYO-key multimodal options exist (Cohere, Voyage, Google). The embedder interface must be provider-agnostic and record model+dimension+quantization per collection, since dims vary (256-2048) and mixing models in one index is invalid.
- **OpenAI still has no multimodal embedding model as of mid-2026 — text-embedding-3 (late 2023) remains its latest, and it has fallen off the top of MTEB.** — _https://app.ailog.fr/en/blog/news/embedding-models-2026 ; https://mixpeek.com/curated-lists/best-multimodal-embedding-models_
  - Implication: The single most common BYO key cannot do native multimodal embedding. Launch architecture must therefore work text-only: describe-then-embed (any chat VLM writes the description, any text embedder indexes it) must be a first-class path, not a fallback hack.
- **Direct multimodal (visual) embedding beats describe-then-embed by ~32% relative mAP@5 and ~20% nDCG@5 in controlled comparisons, because captions lose layout, chart color-coding, table structure, and spatial relationships.** — _https://arxiv.org/html/2511.16654_
  - Implication: Describe-then-embed is acceptable for launch but measurably lossy on visually rich content (slides, dashboards, invoices). Native multimodal single-vector should be a fast-follow, and the schema should let a media object hold BOTH a caption-derived text vector and a native visual vector.
- **Late-interaction visual retrieval (ColQwen3-4B, ColModernVBERT-250M, Jina v4 multi-vector at 90.17 ViDoRe) is the accuracy frontier for document retrieval, but ColPali-style models emit ~1,024 x 128-d patch vectors per page, and MaxSim over disk-resident multivectors adds heavy storage cost and query latency.** — _https://weaviate.io/blog/late-interaction-overview ; https://qdrant.tech/documentation/tutorials-search-engineering/using-multivector-representations/ ; https://arxiv.org/pdf/2512.02660_
  - Implication: Late interaction cannot be the default inner-loop index if the target is low tens of ms. Support it only as (a) an unindexed rerank stage over the dense top-k (Qdrant's recommended pattern: store multivectors without HNSW) or (b) via MUVERA-compressed single vectors. Ship it post-launch as an opt-in 'high-fidelity documents' mode.
- **MUVERA (Google, NeurIPS 2024, now in Qdrant/Weaviate) transforms multi-vector sets into fixed dimensional encodings searchable with standard MIPS/HNSW — ~10% better recall at 90% lower latency than prior multi-vector retrieval, with exact MaxSim rerank on a small candidate set.** — _https://research.google/blog/muvera-making-multi-vector-retrieval-as-fast-as-single-vector-search/ ; https://qdrant.tech/articles/muvera-embeddings/_
  - Implication: This is the bridge that makes late-interaction compatible with the latency requirement: FDE vector in the fast index, patch vectors in cold storage for rerank. Design the schema now so a media chunk can carry one 'primary' indexed vector plus optional auxiliary multivectors.
- **Jina embeddings v4 (3.8B, open weights, Qwen2.5-VL-based) is the strongest self-hostable multimodal option, supporting BOTH single-vector and multi-vector output from one model (84.11 ViDoRe dense, 90.17 multi-vector); Nomic Embed Multimodal and Qwen3-VL embeddings are credible open alternatives.** — _https://arxiv.org/abs/2506.18902 ; https://huggingface.co/jinaai/jina-embeddings-v4_
  - Implication: The OSS story doesn't depend on any vendor: users without commercial keys can self-host Jina v4 and get both retrieval modes from one model. Ship a local-inference adapter (e.g., via sentence-transformers/vLLM) alongside API adapters.
- **PDF parsing is commoditized but unevenly benchmarked: Docling leads OSS (~0.877 opendataloader-bench, strong on tables), marker/MinerU trail slightly, commercial Reducto/LlamaParse/Unstructured claim higher but every published benchmark is vendor-run — no neutral benchmark exists.** — _https://pdfmux.com/blog/pdfmux-vs-llamaparse-vs-docling-vs-unstructured-2026/ ; https://unstructured.io/benchmarks ; https://llms.reducto.ai/document-parser-comparison_
  - Implication: Don't build a parser; wrap Docling as the default OSS ingestion adapter with pluggable commercial alternatives (Reducto/LlamaParse/Unstructured) for the hosted tier. Keep parsing strictly at the ingestion edge so parser choice never affects retrieval latency.
- **ASR is a solved upstream problem: Whisper large-v4 (real-time streaming API, Q4 2025), Deepgram Nova-3/4 (~300-450ms streaming latency), AssemblyAI Universal-3 (8.14% WER, built-in diarization). Memory-relevant structure is in the transcript metadata: speaker turns, timestamps, channel.** — _https://callsphere.ai/blog/real-time-asr-2026-whisper-v4-deepgram-nova-4-assemblyai-universal-2 ; https://www.coval.ai/blog/best-speech-to-text-providers-in-2026-independent-benchmarks-and-how-to-choose/_
  - Implication: Do not put ASR in the core. Accept transcripts (with speaker/timestamp structure) as an ingestion format; chunk on speaker turns; store audio-source pointer + time offsets so agents can cite 'who said what when'. Optionally offer transcription adapters in the hosted service.
- **Among agent-memory incumbents, only Cognee has real multimodal ingestion (30+ connectors: PDF, audio auto-transcription, image OCR+caption, video); Mem0 claims PDF/image memory; Zep and Letta remain essentially text/conversation-centric.** — _https://mcp.directory/blog/mem0-vs-letta-vs-zep-vs-cognee-2026 ; https://weavai.app/blog/en/2026/05/09/cognee-2026-review-graphrag-ontology-ai-memory-layer/_
  - Implication: Multimodal done well (native visual embeddings + provenance-preserving schema + scoped retrieval) is a differentiator against Mem0/Zep/Letta, and Cognee's approach (caption/OCR everything to text+graph) is exactly the lossy path the research says to improve on.

### Recommendations
1) LAUNCH (v0): text-canonical, media-aware. Every memory item has (a) a text surface form — extracted text (Docling adapter for PDFs/Office), ASR transcript with speaker turns/timestamps, VLM-generated description for images, or templated serialization for structured CRM records — embedded with the user's BYO text embedder (OpenAI/Cohere/Voyage/Gemini/local); and (b) a MediaObject reference: storage URI, content hash, MIME type, byte size, plus chunk-level provenance (page number, bounding box, audio start/end ms, speaker id). This works with every key people already have, keeps one dense HNSW index per collection, and preserves the ability to hand the ORIGINAL media to a VLM agent at generation time (retrieve-by-text, answer-from-pixels — a cheap way to get most multimodal value with zero index changes).

2) FAST-FOLLOW (v0.x): native multimodal single-vector. Add an embedder capability flag (text | multimodal | multivector). For users with Cohere embed-v4 / voyage-multimodal-3.5 / Gemini Embedding 2 keys or self-hosted Jina v4, embed page screenshots and images directly — one vector per page, same index, same latency. Store it as an additional named vector on the same chunk row so text-vector and visual-vector coexist; never mix models/dims within one index, and record {model_id, dim, revision} on every embedding to enable lazy re-embedding when users switch models.

3) LATER (v1+): late interaction as opt-in 'high-fidelity documents' mode, never the default. Two supported patterns: (a) dense first-pass then MaxSim rerank using unindexed stored multivectors (Qdrant pattern) — bounded latency because rerank touches only top-k; (b) MUVERA fixed-dimensional encodings in the fast index with exact rerank. ColModernVBERT/ColQwen3 via local inference for OSS users; hosted tier can run it as a managed service. Video and native audio embeddings (voyage-multimodal-3.5 video frames) also belong here.

4) SCHEMA PRINCIPLES: separate three layers — MediaObject (immutable blob + hash), Representation (derived: extraction, transcript, caption, thumbnail; each versioned with the pipeline that produced it), and Chunk (retrieval unit: text, named vectors, provenance offsets, and the scoping payload: tenant_id, entity_ids, ACL principals — indexed for PRE-filtering, since post-filtering breaks both latency and the permission guarantee). Freshness (CDC updates) then means: new source version → new Representations → upsert Chunks by stable chunk-id → stale vectors garbage-collected; the media hash makes idempotent re-ingestion trivial.

5) OSS/CLOUD SPLIT: keep in OSS core — the schema, embedder adapter interface, Docling-based parsing, transcript ingestion, describe-then-embed pipeline, and all retrieval modes. Reserve for cloud — managed embedding/parsing/ASR (no keys needed), managed late-interaction infrastructure (GPU inference + multivector storage economics are genuinely painful to self-host), and cross-source freshness orchestration at scale. This split is credible because the expensive-to-operate parts (GPU embedders, multivector storage) are exactly the parts enterprises will pay to not run.

## Open-Core Strategy & Licensing

The 2024-2026 relicensing wars produced a clear verdict by mid-2026: restrictive relicensing after adoption (BSL, SSPL, or feature-stripping) reliably triggers hyperscaler-backed forks that win — Terraform→OpenTofu (Linux Foundation, 10M+ downloads), Redis SSPL→Valkey (now the default on AWS ElastiCache and Google Memorystore, forcing Redis to add AGPLv3 back in May 2025), and MinIO's 2025 console-stripping ended with the OSS project in "maintenance mode" and its reputation destroyed. Every successful fork shares the same DNA: permissive license + foundation governance + cloud-provider backing. Meanwhile the companies that never touched their license and never gated engine features — Qdrant (Apache 2.0, full-featured single binary), Temporal (MIT server), Supabase (MIT/Apache, $170M ARR May 2026, $10.5B valuation), LiveKit (Apache 2.0, $1B valuation Jan 2026), ClickHouse (Apache 2.0 core) — are the commercial winners of this cohort. Their shared moat is not the license; it is a closed-source *control plane*: ClickHouse's SharedMergeTree, Neon's control plane (Apache engine, but self-hosting the disaggregated architecture is impractical — Neon still sold to Databricks for $1B), Temporal Cloud, Qdrant Managed/Hybrid Cloud.

What actually converts OSS users to paid is consistent across all seven: (1) ops burden — running a distributed stateful system in production (HA, upgrades, shard rebalancing, backups/PITR) is the #1 driver; Temporal's and Supabase's own docs lead with this; (2) compliance gates — SSO/SAML, SCIM, audit logs, SOC 2/HIPAA, org-level RBAC ("risk insurance, not expense"); (3) platform conveniences that only make sense multi-tenant — Supabase's branching, observability, multi-project management, point-in-time recovery are cloud-only while every runtime component stays OSS; (4) managed data movement — Airbyte monetizes hosted connectors with SLAs while keeping the connector SDK MIT. The adoption wedge that precedes all of this is a zero-dependency local experience: Temporal explicitly replaced its docker-compose quickstart with a single binary (`temporal server start-dev`, embedded SQLite + web UI) because "Docker remains a foreign concept to many developers"; Qdrant's single self-contained Rust binary and LiveKit's identical-API promise (switch between self-hosted and Cloud without changing a line of code) follow the same logic.

Two findings are specific to our space. First, the agent-memory category already has licensing norms: Mem0, Letta, and Zep's Graphiti are all Apache 2.0 cores with hosted platforms — an AGPL or BSL agent-memory project would be the outlier and would lose the enterprise-legal-approval race (many corporate policies still block AGPL dependencies even after Elastic/Redis rehabilitated it). Second, Airbyte pivoted directly into our territory in May 2026 with "Airbyte Agents" and a "Context Store — a data index optimized for agentic search" with 600+ connectors and Salesforce/HubSpot write-back — both validation of the concept and the clearest competitive threat, and a reason our connector strategy cannot be entirely cloud-gated.

## Agent Memory Science & Craft

The agent-memory field converged in 2025-2026 on a consistent cognitive taxonomy (working/episodic/semantic/procedural) and a tiered production pattern: a small always-in-context core, a retrieval-backed store, and an explicit forgetting policy. But the more consequential 2026 development is a fork in WRITE-PATH philosophy between the two leading OSS systems. Mem0 v3 abandoned write-time conflict resolution entirely (single-pass ADD-only extraction, contradictions resolved at read time via hybrid semantic+BM25+entity retrieval), which halved extraction latency but leaves contradictory facts coexisting in the store — its OSS dedupe is a literal MD5 text hash, so "moved from Chicago to New York" yields two live high-scoring vectors. Zep/Graphiti (v0.29.x, Apache-2.0, 28.6k stars) went the opposite way: a bi-temporal knowledge graph where every fact edge carries event-time and ingestion-time, and new contradicting information sets invalid_at on the old edge (invalidation, never deletion), enabling "what is true now" and "what was true then" queries. Newer academic work (MemStrata, June 2026) supplies the crucial mechanism finding: embedding similarity is structurally incapable of distinguishing contradictions from duplicates (0.59 AUROC — near chance, because a contradiction is a minimal edit of the original), so deterministic supersession keyed on (subject, relation) is the only reliable way to retire stale values; RAG baselines serve superseded facts 15-40% of the time, deterministic supersession ~0%.

The benchmark landscape is badly compromised and should be treated as marketing until independently reproduced. Audits found 6.4% of the LoCoMo answer key is simply wrong and its LLM judge accepts 63% of intentionally wrong answers; Zep documented that Mem0's cross-vendor evaluation misconfigured Zep (wrong user model, mishandled timestamps, serialized searches); independent reproduction (maximem, 2026) found Mem0's claimed 93.4% LongMemEval was actually 73.8% under a neutral judge, with the gap traced to 14 dataset-specific equivalence rules and biased judging prompts baked into the eval harness. LongMemEval-S now fits inside modern 1M-token context windows, so it tests context stuffing, not memory; a full-context baseline beats most memory systems on LoCoMo. Successors (LongMemEval-V2 May 2026, BEAM, StreamMemBench) push toward streaming, knowledge-update, and agent-trajectory evaluation. Meanwhile security research formalized memory poisoning as OWASP ASI06 (2026 Agentic Top 10): MINJA-class injection succeeds >95% against production agents and AgentPoison achieves >80% attack success at <0.1% poison rate — a shared cross-agent memory is a poison amplifier by construction, making write-path provenance and scope-sound retrieval first-class requirements, not features.

For the product's core question — what memory model lets "opportunity updated" cleanly supersede the old value — the research points unambiguously at a layered hybrid, with a key insight the conversation-memory vendors underweight: enterprise data arriving via CDC from systems of record has authoritative IDs and field names, so supersession there is DETERMINISTIC (key = entity_id + field; new value retires old, bi-temporally versioned) and needs no LLM at all. LLM-based fact extraction and temporal-edge invalidation (the Graphiti machinery) is only needed for the unstructured minority (conversations, docs, email) where subject/relation must be inferred. Systems that run every update through an LLM pipeline inherit extraction error rates (up to 30% format failures on weaker backbones per the Anatomy of Agentic Memory study), cost, and seconds of write latency for data that was already structured at the source. On the read path, no current vendor hits the project's low-tens-of-ms target (Mem0 p95 ~200ms, Zep p95 ~300-630ms); getting there requires zero LLM calls on the read path — precomputed current-truth views, hybrid vector+BM25+graph indexes, and deterministic scope filters — which the layered model makes possible.

### Key findings
- **The field converged on a four-type taxonomy (working/in-context, episodic, semantic, procedural, per Tulving 1972) and a standard production pattern: small always-in-context core + retrieval-backed store + explicit forgetting policy; hybrid vector-graph backends are now the recommended default for complex workloads.** — _https://jobsbyculture.com/blog/ai-agent-memory-systems-guide-2026 ; https://arxiv.org/html/2602.19320v1 (Anatomy of Agentic Memory, Feb 2026)_
  - Implication: Our schema should natively distinguish these types (they have different write paths, TTLs, and scoping rules) rather than storing everything as undifferentiated chunks. For a SHARED enterprise memory, the semantic layer (entity facts) dominates; episodic (per-agent interaction logs) and procedural (playbooks) should be separate, differently-scoped stores.
- **Mem0 v3 (2026) abandoned write-time ADD/UPDATE/DELETE conflict resolution for single-pass ADD-only extraction with read-time resolution via hybrid semantic+BM25+entity retrieval. This cut extraction latency ~50%, but OSS v3 dedupes with a strict MD5 text hash, so semantic contradictions (Chicago vs New York address) coexist as separate live vectors that both retrieve with high scores.** — _https://docs.mem0.ai/migration/oss-v2-to-v3 ; https://aireviewzones.com/mem0-review/ ; https://arxiv.org/html/2504.19413v1 (original Mem0 paper)_
  - Implication: Read-time-only conflict resolution is unacceptable for enterprise facts where a stale price or opportunity stage is a correctness bug. We should resolve conflicts at write time for anything with a deterministic key, and treat Mem0's approach as evidence that write-time LLM arbitration was too slow/costly — not that supersession itself should be skipped.
- **Zep/Graphiti (Apache-2.0, v0.29.2 June 2026, 28.6k stars) implements a bi-temporal model: every fact edge carries event time (when true in the world) and ingestion time (when the system learned it), with valid_at/invalid_at windows. Contradicting information sets invalid_at on the old edge — invalidation, never deletion — supporting point-in-time ('as-of') queries. It ingests JSON business data, chat, and text into one graph with custom entity/edge types (episodes → entities → fact triples → communities), on Neo4j/FalkorDB/Neptune, with hybrid semantic+BM25+graph retrieval and no LLM on the read path.** — _https://github.com/getzep/graphiti ; https://arxiv.org/html/2501.13956v1 (Zep paper) ; https://help.getzep.com/adding-business-data ; https://help.getzep.com/graphiti/core-concepts/custom-entity-and-edge-types_
  - Implication: Graphiti is the closest existing OSS system to our requirements and validates bi-temporal fact invalidation as the production-proven supersession mechanism. It is also a competitor/reference: our differentiation is deterministic CDC-native ingestion of structured records (Graphiti still runs LLM extraction over JSON episodes), permission-aware retrieval, and much lower read latency.
- **MemStrata (June 2026) proved that embedding similarity cannot distinguish contradictions from duplicates — learned classifiers over cosine similarity score 0.59 AUROC, worse than chance, because a contradiction is a minimal edit of the original fact. Deterministic supersession keyed on normalized (subject, relation) with a bi-temporal ledger (valid_from/valid_to/superseded_by) achieves 0.95-1.00 accuracy on evolving-knowledge benchmarks vs 0.20-0.47 for naive RAG; RAG serves stale facts 15-40% of the time, deterministic supersession ~0%.** — _https://arxiv.org/html/2606.26511 (MemStrata: Temporal Validity in Retrieval Memory)_
  - Implication: This is the load-bearing scientific result for our design: 'opportunity updated' supersession must be STRUCTURAL (keyed on entity+field / subject+relation), never left to vector similarity or LLM judgment at read time. It also means raw-chunk-only memory can never solve staleness by construction.
- **Vendor-run benchmarks are unreliable. LoCoMo audit: 6.4% of the answer key is wrong, the LLM judge accepts 63% of intentionally wrong answers, 56% of per-category comparisons are statistical noise, and a full-context baseline (~73%) beats Mem0's best (~68%). Zep showed Mem0's cross-vendor eval misconfigured Zep (wrong user model, timestamps appended to messages, serialized searches), understating its score by ~10 points. Independent reproduction found Mem0's claimed 93.4% LongMemEval was 73.8% under a neutral judge — the gap came from 14 dataset-specific equivalence rules and 'lean toward yes' judging prompts in the eval harness. LongMemEval-S now fits in 1M-token context windows, making it a context test, not a memory test. Successors: LongMemEval-V2 (May 2026, agent-trajectory memory), BEAM, StreamMemBench (streaming/future-oriented), and the LoCoMo gold-answer errors documented in the Mem0 paper itself.** — _https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/ ; https://www.maximem.ai/blog/state-of-ai-memory-2026-claimed-vs-observed ; https://penfieldlabs.substack.com/p/proposal-a-new-benchmark-for-long ; https://arxiv.org/html/2605.12493v1 (LongMemEval-V2) ; https://arxiv.org/pdf/2606.14571 (StreamMemBench)_
  - Implication: We should not design to, or market on, LoCoMo/LongMemEval numbers. Build an enterprise-specific eval suite centered on knowledge-update correctness (does the agent cite the CURRENT opportunity value?), scoped-retrieval correctness (zero cross-customer leakage), and freshness lag — dimensions existing benchmarks barely test. Publish the harness so results are reproducible; this is a credibility differentiator against gamed vendor numbers.
- **Memory poisoning is formalized as OWASP ASI06 'Memory & Context Poisoning' in the 2026 Top 10 for Agentic Applications. MINJA-class injection achieves >95% success against production agents; AgentPoison achieves >80% attack success at <0.1% poison rate. The 'poison once, exploit forever' class (April 2026) shows a single malicious document becomes a persistent backdoor across all future sessions. Defense requires controls at ingestion, storage, retrieval, and monitoring — no single control suffices.** — _https://futureagi.com/glossary/memory-injection-attack/ ; https://www.llm-hacking.com/hacks/agent-memory-poisoning-asi06.md/ ; https://lyrie.ai/research/research/poison-once-exploit-forever-ai-agent-memory-poisoning ; https://christian-schneider.net/blog/persistent-memory-poisoning-in-ai-agents/_
  - Implication: A SHARED memory multiplies blast radius: one poisoned write can corrupt every agent in the org. We need write-path provenance (writer identity, source system, trust tier), quarantine/review for low-trust sources (web pages, inbound email), content-injection scanning at ingest, and per-scope retrieval isolation as core OSS features — this is also a strong enterprise sales narrative.
- **The 'Governed Shared Memory for Multi-Agent LLM Systems' paper (June 2026) formalizes exactly our product's problem: it identifies four failure classes of ungoverned shared memory (unauthorized leakage, stale propagation, contradiction persistence, provenance collapse), proposes hierarchical scopes (agent-local / team-shared / tenant-global / restricted) with a 'scope-soundness' invariant on every retrieval path, supersession edges with inactive status for outdated rows, and full provenance (writer identity, source system, derivation history). Its production eval found real cross-scope leaks via unguarded GET-by-id paths and ~0.83s write-to-visibility. Parallel industry writing converges on multi-scope tagging (user_id/agent_id/session_id/org_id) and dynamic, task-contextual permissions over static RBAC.** — _https://arxiv.org/html/2606.24535v1 (Governed Shared Memory) ; https://arxiv.org/html/2603.17787 (Governed Memory: A Production Architecture) ; https://atlan.com/know/enterprise-ai-memory-layer/_
  - Implication: Adopt scope-soundness as a formal invariant: every retrieval path (search, get-by-id, graph traversal, MCP resource read) must evaluate policy — the paper's leak was through the path that skipped the filter. Scoping must be enforced in the storage engine, not by the retrieval prompt. Write-to-visibility latency (freshness) should be a tracked SLO alongside read latency.
- **No current memory system meets a low-tens-of-ms read target: Mem0 reports p50 148ms / p95 200ms search; Zep p95 ranges 300ms-632ms depending on configuration; full-context baselines run 9.9-17s. The 'Anatomy of Agentic Memory' study found an 'agency tax' — hierarchical/LLM-mediated architectures cost 1s to 32s per turn — and 4.8-30% structured-output format error rates when weaker LLMs run the memory-update pipeline. Memory relevance ranking has standardized on composite scoring: semantic similarity x exponential recency decay x importance (frequency/explicit weight), with supersession and forgetting both implemented as invalid_at status changes (distinguished by reason), never physical deletes.** — _https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/ ; https://arxiv.org/html/2602.19320v1 ; https://dakera.ai/blog/temporal-memory-ai-agents ; https://arxiv.org/pdf/2602.06052 (memory mechanisms survey)_
  - Implication: Hitting ~10-50ms requires zero LLM calls on the read path: precomputed current-truth projections, ANN + BM25 + graph indexes queried in parallel, deterministic scope filters pushed into the index, and async-only LLM work (extraction, summarization, contradiction detection). Composite similarity-recency-importance scoring should be a pluggable ranking function; decay applies to episodic/conversational memory but NOT to system-of-record facts, which are current until superseded.
- **Provenance-grounded designs (Eywa, May 2026) separate immutable evidence roots (raw episodes/source records, never rewritten) from derived beliefs (facts/summaries that can be superseded as new evidence arrives), with full derivation chains reconstructable at sub-second per-hop latency. This 'evidence vs belief' split is echoed across Graphiti (episodes as ground truth), the governed-memory papers, and practitioner writing.** — _https://arxiv.org/pdf/2605.30771 (Eywa: Provenance-Grounded Long-Term Memory) ; https://neo4j.com/blog/developer/graphiti-knowledge-graph-memory/_
  - Implication: Our storage model should hard-separate an immutable, append-only evidence layer (CDC events, webhook payloads, doc versions, transcripts — the audit log) from mutable derived layers (facts, entity profiles, summaries). This gives free replay/rebuild of derived layers when extraction improves, per-fact citations for agents, and poisoning forensics.

### Recommendations
1. MEMORY MODEL: Adopt a four-layer hybrid, not any single representation. (L0) Immutable evidence log: append-only raw episodes — CDC events, webhook payloads, doc/page versions, transcripts — with provenance (source system, writer, trust tier, ingest time). Never rewritten; everything else is derivable from it. (L1) Canonical entity-record layer: typed, versioned mirrors of system-of-record objects (Account, Contact, Opportunity, Ticket) updated by DETERMINISTIC upsert keyed on (source, entity_id, field) with bi-temporal versioning (valid_from/valid_to/superseded_by). This is how 'opportunity updated' cleanly supersedes the old value — no LLM involved, supersession is a keyed write, freshness lag is just CDC lag. (L2) Extracted-fact layer: bi-temporal (subject, relation, object) facts produced by async LLM extraction ONLY over unstructured sources (conversations, docs, email), with Graphiti-style edge invalidation; where a fact's subject resolves to an L1 entity, link it, and let L1 win conflicts (system of record outranks conversational inference). (L3) Derived views: entity summaries/profiles and precomputed 'current truth' projections rebuilt asynchronously for fast reads. Do not run structured records through LLM extraction — that is the single biggest design error to avoid, and it's what today's conversation-memory vendors (including Graphiti's JSON-episode path) do.

2. SUPERSESSION MECHANICS: Make supersession structural and deterministic per MemStrata — keyed on entity+field (L1) or normalized subject+relation (L2) — never vector-similarity- or read-time-LLM-based (0.59 AUROC; contradictions look MORE similar than paraphrases). Invalidate, never delete (invalid_at + reason ∈ {superseded, forgotten, retracted, poisoned}), preserving as-of-time queries and audit. Default read path serves only currently-valid facts.

3. READ PATH: Zero LLM calls at read time. Parallel hybrid retrieval (ANN vector + BM25 + graph-neighborhood expansion) over precomputed projections, with scope filters compiled into the index query (metadata filtering / partition-per-tenant), and composite similarity×recency×importance ranking applied only to episodic/conversational memory (L1 facts are current-until-superseded, no decay). This is the only credible route to the 10-50ms target; best-in-class today is ~150-200ms p95 (Mem0) and 300-630ms (Zep), so there is real headroom to differentiate.

4. SCOPING & SECURITY AS INVARIANTS: Implement the governed-memory 'scope-soundness' invariant — every retrieval path (search, get-by-id, graph traversal, MCP tool/resource) evaluates policy in the storage engine; the documented production leak came through an unguarded get-by-id path. Model scopes hierarchically (org/tenant → team → agent → session) plus entity-scoping (customer A vs B) and principal-based ACL inheritance from source systems (a doc's Google Drive ACL follows it into memory). Treat memory poisoning (OWASP ASI06) as a first-class threat: trust-tiered writes, quarantine for low-trust sources, injection scanning at ingest, per-write provenance enabling surgical rollback of everything derived from a poisoned episode (which L0→L2 derivation links make possible).

5. EVALUATION: Do not chase LoCoMo/LongMemEval — both are compromised (wrong gold answers, gameable judges, fits-in-context) and vendor numbers demonstrably don't reproduce. Ship an open, reproducible eval harness focused on what enterprise buyers actually need: knowledge-update correctness (stale-fact citation rate after a CDC update — target ~0% per MemStrata vs 15-40% for RAG), scoped-retrieval correctness (zero cross-entity/tenant leakage under adversarial probes), write-to-visibility freshness lag, and p95 read latency under concurrent agents. Publishing honest, reproducible numbers is itself a differentiator in a market where the two leading vendors have publicly accused each other of benchmark manipulation.

6. POSITIONING VS EXISTING OSS: Graphiti is the closest prior art and validates bi-temporal invalidation; Mem0 validates demand for a simple add/search API. Neither is CDC-native, permission-aware at the storage layer, nor fast enough for inner-loop use. Consider Graphiti-compatible concepts (episodes, facts, valid_at/invalid_at) to ease migration, while differentiating on: deterministic structured-record supersession, source-ACL-aware retrieval, sub-50ms reads, and an MCP-first interface serving all four layers (evidence citations included) to any framework.
